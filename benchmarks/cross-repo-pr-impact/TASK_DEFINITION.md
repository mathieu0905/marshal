# 跨仓评测任务定义

版本：2.1
日期：2026-08-31

## 任务边界

数据集向受测系统提供：

- 一个源仓在观察截止时间的候选变更；
- 一个由项目或生态规则预先定义的候选仓目录；
- 目录内各仓在同一截止时间的代码快照。

受测系统先返回有序候选仓列表，并可选择要执行的仓。产品级轨道在预测冻结后由 evaluator 对选中仓运行数据集固定检查，产生独立 A0/A1/A2 结果和证据卡；预测自报的执行结果不计分。数据集不要求系统从整个 GitHub 或其他托管平台发现候选仓。

统一的是输入和输出接口，不是标签结论。历史适配与可执行因果破坏必须按证据层分别计分和解释。

## E0：非评分候选线索

协调链接、依赖声明或目录关系只能说明某仓值得审查。单独的 E0 不构成评分目标，也不能证明发生破坏。

## E1：历史适配排序

### 问题

给定源仓 PR 的开单差异和同项目候选仓时点代码，排序返回后来出现过已核验实现、适配、配置或验证变更的仓库。

它回答：

> 在已知候选仓中，哪些仓库有可核验的历史采纳或适配记录？

它不回答源变更一定会破坏哪些仓库、目标集合是否完整、未标注仓库是否不受影响，或系统是否知道何时停止。

### 标签

`specification_proven` 和 `implementation_proven` 经现有人工语义确认后进入 E1。单独的 `coordination_proven` 只属于 E0 候选线索，不进入 E1。

### 指标

报告 known-target macro recall、MRR、Recall@1/3/5、预测仓数量和召回-工作量关系。额外预测记为 `unjudged`。不报告 precision、F1、accuracy、AP、误报率或 specificity。

## E2：可执行因果破坏

### 问题

给定源仓在失败臂中的差异和失败构建使用的候选仓代码，排序返回至少一个必须配套修改才能使同一任务恢复的目标仓，并指出失败机制与检查位置。

它回答：

> 只采用源变化时，哪个候选仓在固定任务中失败；只加入哪个精确目标修改后，同一失败消失？

### 最低准入

1. A0 使用旧源组合，目标任务通过；
2. A1 只引入源变化，目标任务失败；
3. A2 保持 A1 输入，只加入对应目标适配，原失败签名消失；
4. 三臂实际消费各自指定版本或源码；
5. 失败机制与目标适配位置直接对应；
6. 仓库别名、多模块和共享修复先折叠为独立关系单元。

`ci_contrast_proven` 和 `executed` 只是 E2 候选，必须重核上述条件。普通协调链接、绿色构建、双版本差异或维护者后续宽迁移均不足以自动进入 E2。

### 指标

E2 单独报告目标仓找回、MRR、Recall@K、检查位置找回、可运行检查率、失败/恢复判断和 `not_assessed` 比例。执行正确率的分母包含全部 E2 目标，不能只统计成功执行的预测。

标签证据与系统执行证据必须分开。前者证明题目答案为 strict-E2；后者证明受测系统在本次冻结预测之后实际运行。缺失 evaluator-owned execution result 的目标保持 `not_assessed`，不得使用预测中的字符串声明替代。

## E3：有界负例

候选仓只有在固定代码、固定源输入和相关任务下确认消费变化表面，并在 A0/A1 中稳定通过，才能获得 E3。它只表示在该命令和输入范围内未观察到影响。

E3 不是 E2 的准入条件。如果同一 bounded universe 的正负候选没有完整判定，只报告 false-alarm、abstention 和预测数量，不报告 precision/specificity。v1 输出中的 `no_cross_repo_impact` 只能用于这样的 E3 范围，不能用于 E1 主集中未标注的候选仓。

## E4：兼容变化

独立源变化真实进入相同消费表面，而候选任务前后通过时，形成 E4。它用于测量系统对兼容变化的克制，不要求每个 E2 案例都配一个 A3。

## 逃逸棘轮顺序任务

棘轮不是单次案例属性。顺序任务先观察一次已确认逃逸，随后登记永久检查，再提交同触发范围的复发事件和一个无关控制。通过要求：检查登记成功、复发自动调度、真实失败证据导致阻断、无关控制不调度。只验证数据库 CRUD 或只生成 review lens 不算端到端通过。

## 候选仓目录

候选目录必须与单条隐藏标签独立，记录来源规则和仓库纳入理由，且生成规则可跨同类源事件复用。当前样本 observed-once 的独立大目录不等于量身定制单例目录，但必须单列 selection rule 和豁免理由。非目标候选默认是 `unjudged`，不能仅因位于目录中或测试绿色而成为 E3。

当前 12 个目录中，Ethereum、OpenTelemetry 与 Rust 已按独立项目/生态来源重建并覆盖 71 条案例；其余目录仍由已知目标与手工干扰仓合并，且四个目录只服务一条案例。因此 100 条全集仍不产生正式无泄漏主分数。三个合格目录中另行发布的 50 条最终 E1 子集已完成逐条证据审计。完整要求见 `CANDIDATE_BOUNDED_DESIGN.md`。

## 输入可见性

推理阶段遵循 `INPUT_SPEC.md` 并关闭网络。受测系统不能读取隐藏 case、目标 PR、协调尾注、持续集成历史、执行答案或结果目录。OpenDev 邮件补丁必须转换为纯代码差异，不能泄漏 `Depends-On` 或目标地址。

## 数据划分与任务单位

legacy 的 100 条 schema-v1 索引继续全部标为 `test`。50 条最终 E1 子集在独立
发布索引中按完整项目组隔离：OpenTelemetry 为 development、Ethereum 为
evaluation、Rust 为 holdout；同一项目不跨 split。

当前 strict-E2 发布包含 50 条“源事件—目标仓”关系，但候选选择的任务单位是源
事件。相同源仓、base/head、代码 patch、观察截止时间和候选目录的关系必须合并为
一个输入，并把全部已知目标作为多目标标签；不得让同一模型输入以多个单目标答案
重复计权。目标修复仍以 50 条关系为任务单位，因为每条关系有独立目标 base、固定
检查和维护者补丁。

现有 E2 标签已进入公开 Git 历史，因此当前 evaluation/holdout 只能解释为公开评测
划分或 holdout proposal，不能称为真正盲测。真正 blind holdout 必须来自从未公开的
新案例，或由不分发标签的私有 evaluator/server 计分；删除、改名或移动已公开文件
不能恢复盲性。

## 发布边界

E1 与 E2 分别给出规模、目录来源、项目与年份分布、关系分布、证据等级和结果。E1 分数不能支持跨仓破坏发现结论；E2 正例不能自动支持误报率；E3/E4 的结论不能外推到未执行候选仓。

只有候选目录审计、隔离 split、输入可见性检查和相应轨道的实际系统运行完成后，才能发布该轨道的正式比较结果。排序运行不能替代因果执行、克制面或棘轮运行。这些是评测解释条件，不是产品 gate。
