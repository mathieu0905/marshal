# jcabi 项目包正式重复合同

日期：2026-08-24

## 研究问题

在四个固定消费者提交和固定原生命令上，`jcabi-aspects` 的真实破坏性发布是否稳定地产生两个需要配套修复的目标仓与两个命令范围内无需修改的候选仓；维护者修复是否稳定恢复失败；另一个真实相邻发布是否能构成无须配套修改的兼容变化。

零假设是观察到的失败、恢复或继续通过来自依赖缓存、短时环境变化或单次偶然结果。备择假设是五个配置在三个独立重复中保持预期方向，且每次都明确解析指定的 `jcabi-aspects` 版本。

这是主动反事实项目包实验，不是历史同期事件重放。统计单位是整个项目包；仓库任务和重复运行只提供证据，不增加独立案例数。

## 固定输入

| 仓库 | 消费者提交 | 命令 | 当前标签范围 |
|---|---|---|---|
| `jcabi/jcabi-s3` | `0efa37ae2c431ae148e921dc3c1a9fcb8aa2bd3a` | `mvn clean test -B` | 正例；编译及 12 项单元测试 |
| `jcabi/jcabi-simpledb` | `4af3ea931691caa0a667852b626485b1b0cbffcf` | `mvn clean test -B` | 正例；编译及 5 项单元测试 |
| `jcabi/jcabi-w3c` | `4054d4ad3c26607ec1bd8221b2bb1faa70ee78b0` | `mvn clean test -B` | 限定负例；编译及 9 项单元测试 |
| `jcabi/jcabi-maven-plugin` | `c6d7c3d883b5176a0532516af477f77f96884ebb` | `mvn clean verify -B` | 限定负例；单元检查及 5 个集成场景 |

固定顺序为 `jcabi-s3`、`jcabi-simpledb`、`jcabi-w3c`、`jcabi-maven-plugin`。使用 OpenJDK 11 和 Maven 3.9.8；每个“配置与重复”组合建立新的 Maven 本地仓，每个消费者建立新的 Git 副本。

Maven 本地仓允许从同一只读依赖种子复制，以减少重复下载。它仍是运行间彼此隔离的可写目录；四个版本已在筛选阶段用空目录从远程取得并核对。正式结果必须另行核对实际解析版本，不能仅凭 POM 文本判断。这个效率调整不替代正式代码执行。

## 五个可执行配置

| 配置 | 源版本 | 目标修复 | 预期 |
|---|---|---|---|
| A0 | 0.24.1 | 无 | 四仓通过 |
| A1 | 0.25.1 | 无 | `s3`、`simpledb` 因 `Tv` 缺失失败；其余两仓通过 |
| A2 | 0.25.1 | 只向两个目标仓应用维护者修复片段 | 四仓通过，A1 失败签名消失 |
| A3 前臂 | 0.22.2 | 无 | 四仓通过 |
| A3 后臂 | 0.22.3 | 无 | 四仓通过 |

A3 是独立的 0.22.2 到 0.22.3 前后发布子对照，不能把 A0 的 0.24.1 当作它的基线。两个子臂各运行三次。完整 0.22.3 发布含行为、打包、依赖及内部重构变化；当前任务覆盖 `MethodValidator` 相邻路径，但不直接触发 `HV000151` 分支，因此只能支持固定闭集在已执行范围内无需适配，不能支持该异常分支等价。

A2 的两个补丁来自维护者真实修复，只抽取与 `Tv` 移除直接相关的片段：

- `../jcabi-s3-tv-removal-target-repair.patch`
- `../jcabi-simpledb-tv-removal-target-repair.patch`

两个限定负例在 A2 中没有目标修改，因此 A2 与 A1 的仓库内容相同；仍执行 A2 是为了测量整个项目包在“只修复真目标”后的状态。

## 重复与证据

每个配置执行三个独立重复，共 15 次项目包运行和 60 次仓库命令。筛选阶段已有运行不计入这三次重复。

每次保存：

- 消费者提交、应用后的 Git 差异与状态；
- 完整 Maven 日志、退出状态、开始和结束时间、耗时；
- Maven 本地仓及插件嵌套仓中指定版本发布物的解析证据；
- Surefire、Maven Invoker 和嵌套集成测试报告；
- Java、Maven、操作系统及运行根目录。

运行目录是临时执行面，原始日志和报告复制到本目录。临时目录不作为长期证据。

## 判定

最低有效条件：60 个仓库命令均实际启动；每个有效命令都能核对指定版本；A1 两个目标的三次失败均为相同 `Tv` 缺失签名；其余预期通过配置均完成对应任务。

项目包达到稳定证据的条件：所有有效运行中至少 90% 符合预期，且没有方向相反的稳定结果。若出现网络或依赖源故障，记录为环境失败并在新目录重试一次；若出现测试失败、编译失败或版本解析错误，不得自动重试为绿色，必须先归因。

以下任一情况会使当前项目包结论保持不确定：

- 指定版本没有被实际消费；
- A1 失败签名漂移到与 `Tv` 无关的位置；
- A2 改动超过已记录的维护者修复片段；
- A3 任一消费者需要代码修改或同一任务稳定失败；
- 结果依赖运行顺序或共享可写缓存。

本合同不负责独立语义复核。两个维护者修复片段和 A3 完整发布仍须由独立复核者判断；执行者自己的再次阅读不能冒充第二位标注者。
