# 现有五个项目包的模型语义复核

复核日期：2026-08-24

## 复核身份与结论口径

本次复核由未参与这些运行的模型会话完成，使用了正式运行合同、机器摘要、源版本差异、维护者提交、抽取补丁、测试日志摘要和已有去结论复核材料。它可以作为独立于执行过程的语义质检，但**不是第二位人工标注者，也不是正式人工盲审**。本文件不把模型判断写回正式标签。

逐包结论如下：

| 项目包 | 模型结论 | 可保留内容 | 必须收窄或补齐的内容 |
|---|---|---|---|
| Alembic 到六个 OpenStack 消费仓 | 接受，限命令合同 | 一个破坏变化案例、一个兼容变化案例 | Cinder 是测试/迁移一致性规则适配；五个负例只限 MySQL 模型同步 |
| jcabi-aspects 到四个消费仓 | 需收窄 | 一个破坏变化案例，两个正例、两个限定负例 | 0.22.2 到 0.22.3 未证明真实行为分支进入测试，不能接受 A3 |
| SLF4J 到四个消费仓 | 需收窄 | Jadler 正例；Password4j、Spotless 的限定合同；A3 的有限初始化结论 | RabbitMQ 的日志提供方实际失效，不能标为无影响负例；闭集只剩三个已判定仓 |
| terser 到四个消费仓 | 需收窄 | 一个共同破坏变化案例，三个不同类型正例和一个 Angular 合同负例 | A3 没有变化表面证据且未包含 Angular；Preconstruct 只能作为子测试判定 |
| SnakeYAML 到四个消费仓 | 接受，限命令合同 | 一个破坏变化案例、一个兼容变化案例 | A3 只覆盖 3 MB 判断的正常分支，不覆盖超限异常 |

因此，按“破坏变化和兼容变化都具备语义证据”的完整四臂口径，模型复核接受 **2 个项目包**：Alembic 和 SnakeYAML。jcabi-aspects、SLF4J、terser 的破坏臂仍有可用的高证据材料，但当前不能整体算作语义完整的四臂项目包。

## 一、Alembic 到 OpenStack 消费仓

### 结论：接受，严格限制到模型同步合同

1. **破坏变化真实且归因明确。** Alembic 1.19 开始比较检查约束；Cinder A1 三次只在同一个 MySQL `test_models_sync` 中出现相同的 12 表 `remove_constraint` 差异。A0、A1 使用相同 Cinder 基线，A2 保持 Alembic 1.19.1，仅增加目标修复，排除了普通依赖漂移作为主要解释。证据见 `results/requirements-formal-repetitions-2026-08-24/RUN_CONTRACT.md` 和同目录 `summary.json`。
2. **A2 抽取精确，但响应类型应写清。** `results/requirements-cinder-active-pilot-2026-08-24/a2-maintainer.patch` 只修改 Cinder 的迁移一致性测试过滤器，针对 12 张表的既有检查约束差异；它不修改生产迁移或数据库模型。该目标应分类为“测试/迁移一致性规则适配”，不能泛称生产修复。
3. **五个限定负例可接受。** Heat、Ironic、Keystone、Nova、Placement 都实际安装 1.19.1 并执行各自 MySQL 模型同步测试，覆盖 Alembic 自动生成比较路径。结论上限是“该固定提交的指定 MySQL 模型同步合同无需目标修改”，不包括其他数据库、迁移命令或运行时路径。
4. **A3 可接受。** 1.17.2 到 1.18.0 引入自动生成插件和比较器分派重组；六仓的模型同步命令都会构造自动生成上下文并经过比较器分派。它满足“真实变化代码进入执行路径”，但不证明第三方插件、全部方言分支或 1.18.0 的所有行为。

### 统计单位

- 一个项目包；
- 两个不同源变化输入：破坏变化和兼容变化；
- 每个输入各有六个仓库级判断，共 12 个仓库级判断；
- 90 条命令只是五个配置、六仓和三次重复的测量，不是 90 个案例；五个干扰仓的 A1/A2 输入相同，不能重复计数。

## 二、jcabi-aspects 到四个消费仓

### 结论：破坏案例接受，A3 拒绝

1. **破坏变化真实。** 0.24.1 发布物包含 `com.jcabi.aspects.Tv`，0.25.1 删除该公开类。`jcabi-s3` 和 `jcabi-simpledb` 的 A1 三次都在原有 `Tv` 使用点编译失败，失败位置稳定。
2. **两个 A2 抽取精确。** `results/jcabi-s3-tv-removal-target-repair.patch` 只把两个 `Tv` 常量替换为相同数值；`results/jcabi-simpledb-tv-removal-target-repair.patch` 完整对应维护者提交中除版本号外的 `Tv` 移除。两者都没有借修改测试期望绕过失败，且恰好消除 A1 的缺类编译错误。
3. **两个限定负例可接受，但只是编译和已运行合同。** `jcabi-w3c` 的主代码与测试代码重新编译并运行 9 项测试；`jcabi-maven-plugin` 运行编译、单元检查和五个集成场景。对“公开类被删除”这种静态破坏，完整编译本身能直接证明固定源码没有该符号依赖；它仍不覆盖未执行配置、外部服务或反射字符串使用。
4. **A3 不满足准入。** 0.22.2 到 0.22.3 的主要可观察行为变化是 `MethodValidator` 对 `HV000151` 的选择性忽略；现有测试明确没有触发这个异常分支。其余消费者主要执行不可变、重试等切面，发布中的字段初始化移动大多是等价重构。仅证明四仓能在两个发布下构建和通过，不能证明真实行为变化表面被测试触及。因此不得把这组绿色结果算成兼容变化案例。

### 统计单位

- 当前可接受的是一个破坏变化案例，含两个正例和两个限定负例；
- A0/A1/A2 的重复不增加案例数；
- 兼容变化输入暂不计数，项目包须更换 A3 或补充能稳定触发真实变化分支的原生合同。

## 三、SLF4J 到四个消费仓

### 结论：需移除 RabbitMQ 负标签，项目包暂不完整

1. **Jadler 的破坏与恢复成立。** SLF4J 2.0 忽略面向 1.7 接口的 Logback 1.2.11 绑定，回退到 `NOPLoggerFactory`；Jadler 随后把它转换为 `LoggerContext`，三次均出现相同五项错误。A2 只把 Logback 改到 1.3.4，且这正是维护者 PR 276 中说明必须与 SLF4J 2 一起更新的目标侧兼容动作。维护者 PR 使用 SLF4J 2.0.3，而主动 A2 固定 2.0.0，所以这里只接受抽取修复，不把维护者完整 PR 当成同一历史执行。
2. **Password4j 可作极窄负例。** 两臂都没有日志提供方，测试实际进入普通日志调用；可支持“无提供方的 206 项原生测试合同无需修改”，不能外推到日志输出或任意提供方组合。
3. **Spotless 可作极窄负例。** 正式合同只保留直接进入两个 `LoggerFactory` 生产路径的三项测试。它支持编译期 SLF4J 使用和这三个方法的合同，不支持全套测试或运行时提供方兼容。
4. **RabbitMQ 不能作无影响负例。** A1 日志已经证明 Logback 1.2.11 被忽略并回退到空实现，即日志输出这一真实行为发生了退化。114 项测试绿色只说明测试没有把日志提供方行为纳入判定，不能推出目标无需适配。对“发现受影响仓库”的任务，把它标成负例会惩罚正确发现提供方不兼容的系统。当前只能记为“单元合同通过、影响标签未知”；若目标合同明确要求保留日志，应进一步作为潜在正例核对 Logback 升级修复。
5. **A3 的有限语义可保留。** 1.7.30 把替代日志器修复、事件重放和工厂清理移入 `finally`。无提供方和不兼容绑定路径会进入这段新控制流，Jadler 的正常提供方初始化也经过统一收尾。当前执行足以支持普通初始化/无提供方路径的兼容结论，但不覆盖新版本专门修复的多线程初始化失败范围。

### 统计单位

- 一个破坏变化来源，不是四个独立案例；
- 模型当前接受一个正例、两个限定负例，并把 RabbitMQ 留为未知；
- 这使破坏案例不再满足既定的四仓最小闭集，三次 60 条命令不能弥补候选语义缺口；
- A3 可作为有限控制证据保留，但整个项目包应在补入可靠第四仓或正确重标 RabbitMQ 后再提升。

## 四、terser 到四个消费仓

### 结论：共同破坏案例成立，A3 拒绝，Preconstruct 降级

1. **共同源行为成立。** terser PR 433 把 `wrap_func_args` 默认值改为真。四仓 A1 使用同一 4.3.0 代码；Assetgraph、UI5 和 Preconstruct 的差异都是匿名函数作为参数时新增括号，Angular 产物中也稳定新增 531 处同类括号。这四仓应统计为一个多目标源变化项目包，而不是三个或四个源案例。
2. **Assetgraph 修复抽取准确。** `results/terser-formal-repetitions-2026-08-24/inputs/assetgraph-repair.patch` 只放宽对应输出正则，A2 恢复单项历史测试。它是测试期望适配，不是生产代码修复。
3. **UI5 修复抽取准确。** `inputs/ui5-repair.patch` 只在三条生产压缩路径设置 `wrap_func_args: false`，与六个输出断言恢复直接对应。实验没有测维护者所说的懒解析性能，因此结论只到输出合同。
4. **Preconstruct 修复内容准确，但执行证据必须降级。** `inputs/preconstruct-repair.patch` 只更新两个历史快照文件，变化逐项对应新增括号和源映射。问题在于 A0、A2、A3 的进程仍因 39 个未选中快照被报告为过期而非零退出。可以使用“选中的三个用例和 35 个快照”作为结构化子判定，但不能写成命令通过或原生测试恢复；在主证据强度分层中应低于另外两个正例。
5. **Angular 的限定负例可接受。** 两臂同一原生差异化构建合同通过，而且输出比较证明八个包实际进入变化表面。结论严格限制为“该构建合同无需目标修改”；不包括浏览器执行、性能或其他 Angular 工作流。
6. **A3 不满足准入。** 4.2.0 到 4.2.1 含多项真实压缩器修复，但现有材料只显示三个正例仓两侧测试绿色，没有覆盖、输出差异或专门断言证明这些修复中的任一变化表面进入测试。Angular 又没有运行该臂，候选目录也与破坏案例不同。它不能作为四仓项目包的兼容变化案例。

### 统计单位

- 可接受为一个破坏变化案例，含三个正例响应和一个限定负例；
- 三种目标响应应分别标为测试期望、生产配置、快照生成物适配，不应合并成同一修复强度；
- 51 条命令是重复测量；A3 暂不计为第二个案例输入；
- 当前搜索框不完整，四仓闭集只用于受限候选任务，不代表 terser 4.3.0 的完整影响面。

## 五、SnakeYAML 到四个消费仓

### 结论：接受，严格限制到执行合同

1. **破坏变化真实且归因明确。** 1.32 到 2.0 改变 `Constructor` 和 `SafeConstructor` 的构造签名，要求传入 `LoaderOptions`。JClouds 和 ZIO JSON 的 A1 三次均在对应消费点编译失败，A0 通过且 A2 保持 2.0 后恢复。
2. **JClouds A2 精确。** 维护者提交的父提交就是基线；除源版本外，只在两个失败消费点创建并传入 `LoaderOptions`，与两个编译错误一一对应。
3. **ZIO JSON A2 可接受。** 维护者 PR 的实质修复是向 `SafeConstructor` 传入 `LoaderOptions`；随后删除失去用途的 `@nowarn` 和导入属于该修复直接产生的清理，不改变业务语义。主动试验把前版本统一为 1.32，但没有改变目标修复含义。
4. **两个限定负例可接受。** YAML JSON 的多配置解析/读写合同和 YAML Updater 的 146 项模块测试都在 2.0 下实际运行。结论只覆盖记录模块、输入和命令，不代表所有 YAML 特性或仓库其他模块。
5. **A3 证据充分且边界清楚。** 1.31 到 1.32 新增 3 MB 单文档判断；四仓的覆盖报告都显示新增判断行被执行并走正常输入分支。它满足“真实变化表面进入测试”，但未覆盖超限异常分支，不能声称验证新上限的全部行为。

### 统计单位

- 一个项目包；
- 两个不同源变化输入，各有四个仓库级判断，共 8 个仓库级判断；
- 60 条命令是五个配置、四仓和三次重复的测量，不是独立案例；两个限定负例的 A1/A2 输入相同，只计一次标签。

## 汇总后的可发布计数建议

在正式人工复核之前，建议把模型复核后的状态写成：

- **完整四臂项目包候选：2 个**，Alembic、SnakeYAML；对应 4 个源变化输入和 20 个仓库级判断；
- **破坏案例可用但项目包不完整：3 个**，jcabi-aspects、SLF4J、terser；其中 SLF4J 只有三个已判定候选仓，terser 的 Preconstruct 为较低强度子测试证据；
- **不得计入的兼容案例：2 个**，jcabi-aspects 0.22.2 到 0.22.3、terser 4.2.0 到 4.2.1；
- **不得计为限定负例：1 个**，SLF4J 2.0 下的 RabbitMQ JMS Client。

这里的“源变化输入”是交给 Marshal 的独立评测输入；A0、A2 和三次重复是标签证据，不是额外输入。项目包是关系隔离和分割的上层单位，也不能把同一源变化下的多个目标仓拆成独立项目包。
