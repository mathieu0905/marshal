# npm 因果证据来源评估

评估日期：2026-08-24

## 研究问题

公开 npm 破坏变化数据能否补上当前主动项目包过度集中于 Maven 的问题，并同时提供旧组合通过、仅源变化失败、真实目标修复恢复和可靠干扰仓？

## 来源

本轮核对了两套相互独立的公开材料：

1. Mezzetti、Moller 与 Torp 的 NoRegrets 工件，论文为《Type Regression Testing to Detect Breaking Changes in Node.js Libraries》，正式工件 DOI 为 <https://doi.org/10.4230/DARTS.4.3.8>，代码位于 <https://github.com/cs-au-dk/NoRegrets>；
2. Venturini 等人的 npm 客户端恢复研究《I Depended on You and You Broke Me》，论文 DOI 为 <https://doi.org/10.1145/3576037>，开放复现包 DOI 为 <https://doi.org/10.5281/zenodo.5558085>。

第二套复现包采用 CC BY 4.0，公开 64 条破坏记录、44 个顶层客户端、逐案例描述、测试结果和修复链接。本文档只做来源筛选；正式纳入时仍需逐仓核对许可证和重新执行。

## NoRegrets 的实际可用量

仓库当前 `SmallBenchmarkCollection.scala` 有 25 个启用的库条目，但只有 6 个库、11 个版本变化带完整的经典状态：7 个破坏变化、4 个非破坏变化，共 11 个唯一客户端。分布如下：

| 源包 | 破坏变化 | 非破坏变化 | 唯一客户端 |
|---|---:|---:|---:|
| `validate` | 2 | 4 | 2 |
| `debug` | 1 | 0 | 5 |
| `cli-compiler` | 1 | 0 | 1 |
| `buffer-crc32` | 1 | 0 | 1 |
| `async` | 1 | 0 | 1 |
| `chalk` | 1 | 0 | 1 |

它适合提供 A0、A1 和非破坏版本线索，但不天然提供目标消费者修复 A2。典型的 `debug` 2.3.3 到 2.4.0 在五个客户端上失败，2.4.1 在 33 分钟后由源包自身修复；这不是五个目标仓的跨仓适配。`buffer-crc32` 0.2.8 也在约 90 分钟后由源包继续发布修复。完整虚拟机约 6.2 GB，并要求约 30 GB 空间和至少 12 GB 内存；在确认目标修复产率前没有下载它的必要。

结论：NoRegrets 保留为破坏与非破坏版本的筛选来源，不单独升级为四臂项目包来源。

## npm 客户端恢复复现包的实际可用量

复现包的 64 条记录中：

- 32 条首先由源提供方修复；
- 25 条首先由客户端或中间依赖方恢复；
- 7 条未恢复；
- 25 条客户端先恢复记录中，5 条修改代码，7 条同时修改代码和依赖版本，13 条只调整依赖版本；
- 因而有 12 条记录提供真实代码修复线索，明显强于 NoRegrets 的 A2 覆盖。

这些数字按论文复现包字段统计，不等于 25 个独立项目包。同一源变化可能在多个顶层客户端显现，但最终由同一个中间依赖仓修复。按 `provider_version_introduced` 聚合后，只有 5 个源变化重复出现；其中唯一重复的客户端代码恢复是 `babel-preset-es2015` 6.13.1，两条记录都指向同一个 `babel-preset-es2015-rollup` 1.2.0 修复，不能计成两个独立修复仓。

## 优先候选

### escope 到 babel-eslint

这是当前最强的非 Maven 候选：

- `escope` 3.3.0 到 3.4.0 把内部 `referencer` 与 `pattern-visitor` 模块转成默认导出；
- `babel-eslint` 的旧代码直接加载并修改这些内部模块，升级后触发 `TypeError: Cannot read property 'visitClass' of undefined`；
- `babel-eslint` PR 244 在两个加载点兼容读取 `.default`，只增加 6 行；
- 公开复现包记录该源变化通过 `babel-eslint` 影响 6 个顶层客户端，说明它不是只在目标仓自测中出现的人工问题。

本轮以 Node.js 6、目标修复前提交和同一条最小解析命令完成一次三臂筛选：

| 臂 | escope | babel-eslint | 结果 |
|---|---:|---|---|
| A0 | 3.3.0 | 修复前 | 通过，返回 `Program` |
| A1 | 3.4.0 | 修复前 | 失败，出现历史同签名 `visitClass` 异常 |
| A2 | 3.4.0 | 只应用 PR 244 的 6 行修复 | 通过，返回 `Program` |

机器可读摘要位于 `results/escope-babel-eslint-screening-2026-08-24.json`。完整 `npm test` 不能作为本轮合同：现代依赖解析使 A0 也出现 16 个与该异常无关的 Flow 断言失败。定向命令直接覆盖历史异常，但目前仍只有单次筛选，没有三次隔离重复或独立语义复核。

A3 和干扰仓筛选已经结束，不能补成合格四臂包：

- `escope` 3.2.1 到 3.3.0 不是有效兼容臂。目标使用的 ESLint 1.10.3 要求 `escope ^3.3.0`，强制安装 3.2.1 后，npm 会为 ESLint 另装 3.6.0；目标实际加载 3.6.0 并出现同一 `visitClass` 异常；
- 3.4.0 到 3.5.0 在修复后目标上两侧都通过，但在固定的修复前目标上两侧都失败，无法满足 A3 与 A1 使用同一目标基准的要求；
- 代码搜索只找到 `karthikv/tradeship` 中一个非依赖目录副本直接读取 `.default`。它不是能够跨 3.3.0 和 3.4.0 两侧执行同一合同的独立消费仓；其余命中均为提交进仓库的依赖副本。

因此该关系降为三臂正例锚点。普通 `escope` 公共接口消费者没有覆盖受影响的内部模块加载表面，不能充当限定负例。

这个案例还暴露一个重要拓扑：真正需要修改的是中间依赖 `babel-eslint`，而六个顶层仓是失败传播端。正式任务仍以“需要配套修改的仓库”为答案，不能把六个失败端误标为六个修复目标；如果以后报告传播范围，必须与修复位置分字段表达。

它们目前都是线索，不因论文认定或提交存在而自动获得标签。

### test-machinepack 语义拒绝

逐提交和真实客户端重放推翻了复现包对这一记录的简化解释：

- `test-machinepack` 2.1.19 引入本地 `run-instantiated-machine.js`，其输入名定义为 `argins`，但两个调用点仍传 `inputValues`。固定历史依赖后，`machinepack-npm` 的六个无网络测试全部因必需输入缺失而失败；
- 源仓提交 `845d9bd3d25c161e23be4632ddeb34b0deae37a8` 将两个调用点改为 `argins`，并发布为 2.1.22。这是实际恢复六个测试的代码变化；
- 目标仓提交 `dd6f50410d1307c749a0755b815330cb55613b11` 晚四个月才出现，把程序化辅助函数从 `.exec()` 改为 `.switch()`，并将依赖写成从未发布的 `^2.1.23`。七分钟后，目标仓又改为 `^3.0.1`；
- 真实客户端使用 `test-machinepack-mocha` 的命令行入口和原始测试运行器，没有执行上述程序化辅助函数。2.1.19 配修复前目标为 0/6，通过目标的一行 `.switch()` 修改后仍为 0/6；2.1.22 配修复前目标和修复后目标则都为 6/6。

这条记录可以证明公开恢复标签必须重放，但不能证明目标仓修复了源变化造成的破坏。它不进入三臂或四臂储备。机器记录位于 `results/npm-candidate-followup-2026-08-24.json`。

### window-stream 到 Godot

这条恢复记录在执行后成立，但论文对提交顺序的概括需要收紧。Godot 提交 `43878701c82ba1cf192b8b6c5b058ba8987229fd` 先把 `window-stream` 范围从 `~0.4.0` 提高到 `~0.5.0`；约两小时后，`window-stream` 0.5.3 才发布并进入该范围。0.5.3 的提交 `c0a403fa497acff37c5d16194871001ceb7300bb` 让 `TimeWindow` 不再使用事件自带的 `time` 淘汰数据，而是在写入时记录内部 `_time`。

固定 Godot 0.7.9 的修复前提交 `c13aedb0fed7c49acc2988b9e06441d4a4aac33f`，执行窗口、移动平均和元数据三个原生测试文件，共 21 项断言，单次结果为：

| 臂 | window-stream | 目标测试 | 结果 |
|---|---:|---|---|
| A0 | 0.5.2 | 修复前 | 21/21 通过 |
| A1 | 0.5.3 | 修复前 | 20/21 通过；固定时间窗口期望 10、实际 20 |
| A2 | 0.5.3 | 只应用维护者的一处测试输入调整 | 21/21 通过 |
| A3 前 | 0.5.1 | 修复前 | 21/21 通过 |
| A3 后 | 0.5.2 | 修复前 | 21/21 通过 |

A2 只把固定 1000 毫秒窗口的合成输入跨度从 2000 毫秒改为 1000 毫秒，没有带入同一提交的网络测试修改，也没有带入紧随其后的 `window-stream ~0.7.0`、Vows 和开发依赖更新。这说明恢复来自测试合同与新时间语义对齐，不是版本回退或无关改动。

该筛选使用 Node.js 6.17.1，而仓库声明的是 Node.js 0.10.x；Godot 没有锁文件，其余依赖在 2026 年解析后作为共同种子复制。A0 成功和 A1 的单一同路径失败削弱了普通环境漂移解释，但不能声称完整历史环境已经恢复。A3 的 0.5.1 到 0.5.2 修改移动平均的克隆实现；命令进入移动平均及现有 `meta` 路径，但没有直接断言深层对象引用独立性，因此 A3 只作为合同通过筛选，不升级成源修复语义完整覆盖。

当前只接受为单正例四臂锚点。它没有可靠限定负例，也没有完整多仓搜索框；重复三次和独立复核完成前不进入正式标签。机器记录位于 `results/window-stream-godot-screening-2026-08-24.json`。

### terser 到 assetgraph-builder

该线索完成了首轮四臂筛选，但证据类型是输出合同测试适配，不是生产代码修复：

- `terser` PR 433 于 2019-08-27 合入，默认给作为参数传入的匿名函数增加括号；该行为从 4.3.0 起存在。公开复现包记录的实际失败版本为 4.3.9；
- `assetgraph-builder` 的固定基准提交 `ef5be8d4aa37786b6b8529868fcf4b21a614b99c` 通过 `assetgraph` 6.0.0 间接使用 `terser ^4.0.0`，其 `issue #69` 测试严格匹配压缩输出；
- 目标提交 `e4140416e7feaa3d088cf3ad0229fd677ff36dbc` 只修改该测试：放宽正则以同时接受带括号和不带括号的输出，并在同一测试中关闭一处压缩选项。

Node.js 10 下固定 `assetgraph` 6.0.0 和 `terser` 版本后，单次结果为：

| 臂 | terser | 目标代码 | `issue #69` 测试 |
|---|---:|---|---|
| A0 | 4.2.1 | 修复前 | 1/1 通过 |
| A1 | 4.3.9 | 修复前 | 0/1，通过方向为失败；输出多一层函数参数括号 |
| A2 | 4.3.9 | 目标提交后 | 1/1 通过 |
| A3 前 | 4.2.0 | 修复前 | 1/1 通过 |
| A3 后 | 4.2.1 | 修复前 | 1/1 通过 |

目标提交拆分后，只有放宽正则的子集能恢复测试；单独设置 `compressJavaScript: false` 仍为 0/1。这说明需要修改的是测试期望，不是运行时功能。首次安装仍解析了截至 2026 年可用的其他兼容依赖，并额外构建了 `canvas` 2.11.2；三个主臂共享同一依赖目录副本，已固定 `assetgraph` 与 `terser`，但尚未恢复 2019 年全部传递依赖。这些限制在后续正式重复中继续保留，不能把该仓写成生产代码修复。筛选记录位于 `results/terser-assetgraph-builder-screening-2026-08-24.json`。

### terser 的另外两个受影响目标

继续沿同一源行为核对公开修复后，确认 `terser` 4.3.0 的函数参数括号变化至少还有两个独立目标仓需要适配。它因此不再只是单一测试案例，而是一个包含三种目标响应的多目标因果来源。

`SAP/ui5-builder` 的证据最强。PR 331 中的修复提交 `90592f3aec986f44f38fd6c8f9576656ca3fa45f` 在三条生产压缩路径显式设置 `wrap_func_args: false`。维护者说明额外括号会影响 UI5 模块的懒解析性能；本轮只验证输出与历史测试合同，没有独立测量性能。Node.js 10 和历史 `package-lock.json` 下的单次四臂结果为：

| 臂 | terser | 目标代码 | `test/lib/builder/builder.js` |
|---|---:|---|---|
| A0 | 4.2.1 | 修复前 | 17/17 通过 |
| A1 | 4.3.0 | 修复前 | 11/17，通过方向为失败；6 个输出断言均出现新增括号 |
| A2 | 4.3.0 | 只应用生产配置修复 | 17/17 通过 |
| A3 前 | 4.2.0 | 修复前 | 17/17 通过 |
| A3 后 | 4.2.1 | 修复前 | 17/17 通过 |

机器记录位于 `results/terser-ui5-builder-screening-2026-08-24.json`。A2 没有带入同一 PR 的依赖更新提交，因此恢复可以归到三处 `wrap_func_args: false` 配置。三次隔离重复已在统一版本项目包中完成，独立语义复核仍未完成。

`preconstruct/preconstruct` PR 119 则是精确输出快照适配。固定修复前提交 `15caef21f49eaa85334af2cf022fd78ad0b27b71` 后，分别控制直接依赖的 `terser` 版本，只执行覆盖历史改动文件的三个测试：

| 臂 | terser | 目标快照 | 定向结果 |
|---|---:|---|---|
| A0 | 4.2.1 | 修复前 | 3 个测试通过，35 个快照匹配 |
| A1 | 4.3.9 | 修复前 | 3 个测试失败，11 个快照不匹配 |
| A2 | 4.3.9 | 只应用两个历史快照提交 | 3 个测试通过，35 个快照匹配 |
| A3 前 | 4.2.0 | 修复前 | 3 个测试通过，35 个快照匹配 |
| A3 后 | 4.2.1 | 修复前 | 3 个测试通过，35 个快照匹配 |

这里不能写成完整原生测试通过：2019 年的发布依赖已经撤包，临时环境删除了该发布专用依赖并改写了锁文件中的注册表地址；完整测试套件还有两个与本行为无关的 Flow 固件依赖失败。定向测试覆盖历史改动的两个快照文件，但由于跳过其他测试，Jest 会把未执行测试的 39 个快照报告为过期，使通过臂的进程退出码仍为非零。机器记录 `results/terser-preconstruct-screening-2026-08-24.json` 明确保留了这些干预和限制。

三个目标不能等价计数：`ui5-builder` 是生产配置修复，`assetgraph-builder` 是测试期望放宽，`preconstruct` 是生成物快照更新。它们共同证明同一个源行为确实传播到多个仓库，但还不能证明这三个仓库构成完整影响面。

### node-minify 限定负例拒绝

`srod/node-minify` PR 776 只把 `terser` 从 4.2.1 升到 4.3.1，没有目标代码修改，看起来像一个直接的限定负例候选；但其原生测试没有覆盖本次变化表面：

- `packages/terser/__tests__/terser.test.js` 使用三个 ES5 固件，只断言压缩过程无错误且结果非空，不核对生成输出；
- 三个固件含有赋值给对象属性的函数表达式，但没有把匿名函数作为调用或构造参数；
- 直接以 `terser` 4.2.1 和 4.3.9 压缩三个原生固件，三组输出均逐字相同；同一探针中的控制输入 `foo(function () { return 1; });` 则稳定出现预期的新增括号，证明实验确实区分了两个版本。

因此，这条依赖升级即使原生测试通过，也只能说明未覆盖的路径没有暴露失败，不能说明覆盖了变化表面后无需修改。它按“原生合同未覆盖源行为”拒绝为限定负例，不再安装完整历史依赖来制造额外绿色证据。机器记录位于 `results/terser-node-minify-negative-screening-2026-08-24.json`。

`fisker/fis3-plugins` PR 688 也不能补上负空间。它把 `terser` 从 4.2.1 升到 4.3.0，仓库的优化器适配器确实会把任意输入交给 `terser.minify`；但历史仓库没有测试脚本、测试文件或生成输出断言，发布流程只有构建、静态检查和格式检查。这里连 `node-minify` 那样的压缩固件都没有，合并事实不能替代执行合同。该候选按“没有覆盖变化表面的原生可执行合同”拒绝，机器记录位于 `results/terser-fis3-plugins-negative-screening-2026-08-24.json`。

### Angular CLI 限定负例筛选

`angular/angular-cli` PR 15555 把 `@angular-devkit/build-angular` 的 `terser` 从 4.2.1 升到 4.3.1，只修改包声明和锁文件。与前两条拒绝候选不同，它有原生“完整差异化构建”用例：同一输入先生成 ES2015 包，再降级并压缩为 ES5 包，测试断言两类主包的语法层级正确。

Node.js 12.22.12、历史 `yarn.lock` 和两臂独立空优化器缓存下，选中的原生用例在 4.2.1 与 4.3.1 下都通过。为判断绿色结果是否真的覆盖变化表面，本轮只固定测试框架随机生成的临时目录名，并留存用例已经返回的全部 JavaScript 产物；没有改输入、生产路径或断言。结果如下：

| 观察 | 4.2.1 | 4.3.1 |
|---|---:|---:|
| 原生用例 | 1/1 通过 | 1/1 通过 |
| 生成的 JavaScript 包 | 10 | 10 |
| 总字节数 | 1,536,655 | 1,538,773 |
| 匿名函数参数双括号 | 0 | 531 |

10 个包中有 8 个真实变化，两个 runtime 包不变。代表性变化是 `Promise.resolve().then(function(){...})` 变为 `Promise.resolve().then((function(){...}))`。因此它不是“未覆盖表面却绿色”：源行为确实进入主包、polyfills、styles 和 vendor 的 ES2015/ES5 产物，而历史目标无需代码修改即可满足原生差异化构建合同。

这仍只是限定负例筛选。原生用例检查构建成功和 ES5/ES2015 语法层级，没有在浏览器中执行全部产物，也没有测性能；结论只能写成“该历史完整差异化构建合同无需目标修改”。机器记录位于 `results/terser-angular-cli-negative-screening-2026-08-24.json`。后续统一版本重复已完成，但独立语义复核仍未完成。

筛选过程还保留了两个防止误判的对照：普通优化用例的全部十个包在固定临时路径后两版本完全相同；Web Worker 用例虽然含回调，但保留为箭头函数，两个版本的 worker 包也完全相同。只有完整差异化构建自然触及了本次函数表达式参数表面。一次 4.3.1 初跑还因临时替换漏带嵌套 `source-map` 0.6.1 而错误解析到 0.7.3，已作为环境错误丢弃；最终两臂使用相同的历史传递依赖。

### 统一 4.3.0 的三次隔离重复

为避免四个目标分别使用 4.3.0、4.3.1 或 4.3.9 而削弱项目包含义，正式重复将四仓 A1 和三个正例仓 A2 统一为 `terser` 4.3.0；A0 固定为 4.2.1，三个正例仓的 A3 固定为 4.2.0 到 4.2.1。每个仓库、配置和重复使用新的工作目录。三轮共执行 51 个仓库命令，51 项实际版本正确，51 项符合预定方向，总命令时长 665 秒，没有重试。

- Assetgraph 三次 A1 都是 0 项通过，A2 只放宽输出正则后三次恢复为 1 项通过；
- UI5 三次 A1 都有 6 项精确输出断言失败，A2 只应用三处生产配置修改后三次均为 17 项通过；
- Preconstruct 三次 A1 都是 3 个选中用例失败、11 个快照不匹配，A2 三次均为 3 个选中用例通过、35 个快照匹配；由于 39 个未选中快照被报告为过期，所有 Preconstruct 进程仍以非零状态退出，不能写成完整测试套件通过；
- Angular 两臂的原生完整差异化构建用例三次均通过。4.2.1 每轮生成 10 个 JavaScript 包、1,536,695 字节和 0 处新双括号；4.3.0 每轮生成 10 个包、1,538,889 字节和 531 处新双括号。每轮固定 8 个包变化，两个 runtime 包不变。

正式摘要、逐命令日志和去结论复核材料位于 `results/terser-unified-430-repetitions-2026-08-24/`。此前按各仓历史暴露版本完成的 51 条重复保留在 `results/terser-formal-repetitions-2026-08-24/`，只作为行为级重复证据。统一版本首轮曾因嵌套 `source-map` 恢复到错误层级而失败，该轮完整保留但不计入正式结果。

现有执行支持“三种目标响应和一个合同范围内的限定负例在统一源版本下可重复”，还不支持四仓已经构成完整影响宇宙。独立复核者尚未判断共同源行为、三个修复抽取、Angular 结论上限和项目包划分，因此不进入正式精度或停止能力结果。

## 对项目包设计的影响

1. `escope` 到 `babel-eslint` 保留为三臂正例锚点，不再搜索不能满足同一基准合同的 A3，也不把公共接口消费者制造成限定负例。
2. npm 复现包作为 25 条客户端恢复记录的完整搜索框，逐条保留“代码修复、版本调整、源方修复、无法恢复”的原始分类。
3. 版本锁定必须核对实际解析到的传递依赖。首次安装曾先解析到 `escope` 3.6.0，随后强制指定版本才得到正确三臂；只看 `package.json` 范围会产生错误实验输入。
4. 正式重放优先使用案例原生测试；只有原测试因无关依赖漂移失效时，才允许使用直接覆盖历史失败签名的定向命令，并单独标明合同收窄。
5. 传播失败仓与需要修改仓可能不同。评测主标签保持修复位置，传播端只作证据或独立诊断，禁止混合计数。
6. “客户端首先恢复”仍需区分目标修复与源仓自修复；目标提交存在、时间较晚或同时提高依赖下界都不能单独证明恢复归因。
7. 只修改测试期望的恢复关系可以测量输出合同影响，但必须与生产代码修复分层；不能用同一个“目标修复”名称掩盖证据强度差异。
8. 同一源变化出现多个目标修复时，应保留为一个多目标项目包候选，而不是拆成三个独立源案例；目标响应类型和证据强度分别记录。
9. 依赖更新已合并且目标没有代码修改，不构成限定负例。`node-minify` 表明即使仓库有压缩器原生测试，只要固件没有触及匿名函数参数表面，绿色结果仍没有负标签语义；`fis3-plugins` 进一步说明只有构建和静态检查时也不能把合并事实升级为负标签。
10. 限定负例必须同时证明“源输出确实变化”和“目标原生合同仍通过”。Angular CLI 的完整差异化构建满足这两点，但普通优化用例和 Web Worker 用例不满足前一点，因此同一仓库中的绿色测试也不能整体打包成负证据。

## 当前决定

npm 客户端恢复复现包继续作为非 Maven 主动项目包的首要搜索框；NoRegrets 降为版本变化筛选辅助。`escope` 到 `babel-eslint` 是缺少负空间的三臂锚点，`window-stream` 到 Godot 是已经执行的单正例四臂锚点；两者都不能冒充多仓闭集。`test-machinepack` 到 `test-machinepack-mocha` 因恢复归因不成立而拒绝。`terser` 四仓已经完成统一 4.3.0 的三次隔离重复，成为首个具备三种正例响应类型和一个合同范围内限定负例的非 Maven 项目包候选，其中只有 UI5 属生产配置修复。去结论复核材料已经生成，但尚无独立复核结果，因此标签仍未正式接受。`node-minify` 与 `fis3-plugins` 已分别因原生固件未覆盖变化表面和没有原生可执行合同而拒绝。后续继续保留搜索框，不能把一个限定负例解释成完整影响宇宙，也不以正例数量替代闭集证据。
