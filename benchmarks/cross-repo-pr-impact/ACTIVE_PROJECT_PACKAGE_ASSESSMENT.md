# 主动项目包候选评估

评估日期：2026-08-24

## 评估口径

这里的“项目包”以一个源变化和一组真实候选仓为单位。进入主动闭集前，必须同时具备：

1. 同一候选仓基线上的旧组合通过、仅源变化失败、只加入精确目标修复后恢复；
2. 至少两个干扰仓确认消费了同一源变化，并由覆盖相关接口的原生检查验证通过；
3. 一个真实改变相邻契约表面、但不要求候选仓配套修改的兼容源变化；
4. 每个干预臂独立重复，不能把单次历史持续集成结果当成稳定性证明。

历史记录可以使项目包进入“历史锚点”或“待主动重放”状态，但不能替代缺失的干预臂。普通依赖声明、合并状态和绿色构建仍不单独产生标签。

## 当前语义质检状态

截至本次更新，未参与执行的模型会话已对五个已有执行包做独立语义质检。它不是第二位人工标注者，也不产生正式标签；详细依据见 `reviews/model-semantic-review-existing-packages-2026-08-24.md`。

| 状态 | 项目包 | 当前可接受边界 |
| --- | --- | --- |
| 完整四臂候选 | Alembic、SnakeYAML | 破坏变化和兼容变化都进入相关执行合同；仍待第二位人工盲复核 |
| 仅破坏案例成立 | jcabi-aspects | 两个正例、两个限定负例成立；A3 永久拒绝于当前闭集 |
| 闭集不完整 | SLF4J | Jadler 正例和两个窄负例成立；RabbitMQ 受影响但测试未判定，不能作负例 |
| 仅破坏案例成立 | terser | 共同破坏变化成立；A3 无变化表面证据，Preconstruct 仅作子测试证据 |

因此，不能再把“完成三次重复”等同于“完整项目包完成”。当前模型质检层只接受 2 个完整四臂候选；正式人工接受数仍为 0。

## 三、jcabi-aspects 多消费仓

### 当前决定

**破坏三臂具有两个正例和两个限定负例并完成三次重复；原 A3 未进入真实行为分支，已撤销，当前闭集永久保留为三臂案例。**

源变化是 `jcabi-aspects` 0.24.1 到 0.25.1 删除公开类 `com.jcabi.aspects.Tv`。已直接检查 Maven Central 发布物：0.24.1 JAR 含 `Tv.class`，0.25.1 JAR 不含该类。当前闭集只含四个实际执行仓库：

- 正例：`jcabi-s3`、`jcabi-simpledb`；
- 限定负例：`jcabi-w3c`、`jcabi-maven-plugin`。

`jcabi-ssh` 和 `jcabi-github` 仍是 BUMP 记录的失败储备，尚未主动重放，不计入当前闭集。`jcabi-parent` 已排除：它只在依赖管理中声明版本，基线 `mvn clean test` 虽然退出 0，但实际运行 0 项测试，也没有消费代码，不能因为“构建绿”而成为负例。

### 独立于数据集构造者的目标修复

两个恢复臂都优先取自维护者后续真实修复，而不是由数据集作者发明答案：

- `jcabi-s3` 的维护者 PR 372 在提交 `f0910c3004636284a43b60196a1a6cafa3e16477` 中升级到 0.25.1，并把两处 `Tv` 常量替换为相同数值。该提交还混有其他依赖和格式变化，因此 A2 只抽取两处语义相关片段；
- `jcabi-simpledb` 的维护者提交 `e532ee69c9f3ac770088e10224bd1cc167ae5cb3` 说明为 `#155 aspects up`，在失败的 Renovate PR 155 关闭前 14 秒落库，只修改依赖版本和 `RegionITCase` 中的 `Tv` 用法。

两个抽取补丁分别保存在 `results/jcabi-s3-tv-removal-target-repair.patch` 和 `results/jcabi-simpledb-tv-removal-target-repair.patch`，都已核对可直接应用到各自失败臂的目标代码。

### A3 兼容变化筛选

A3 选择 `jcabi-aspects` 0.22.2 到 0.22.3。它是 2016 年的真实相邻发布：公开类文件集合不变，核心行为变化位于 `MethodValidator`，新版本仅忽略 Hibernate Validator 以 `HV000151` 开头的参数约束覆盖异常，其他 `ConstraintDeclarationException` 继续抛出。完整发布还把产物改为 OSGi bundle、更新若干依赖并重构内部字段初始化，因此这里评价的是完整真实发布，不能把结果只归因于这一处异常处理。

四个候选仓仍固定在 2023 年提交。这一组合明确属于“真实历史发布在后续真实消费者上的主动反事实”，不是历史同期发生的跨仓事件。快速筛选保持消费者代码和命令不变，只把依赖从 0.22.2 改为 0.22.3：

| 仓库 | 0.22.2 | 0.22.3 | 当前覆盖判断 |
|---|---|---|---|
| `jcabi-s3` | 12 项通过，7.063 秒 | 12 项通过，7.466 秒 | 覆盖同一发布物中的不可变与重试切面，不直接覆盖验证异常分支 |
| `jcabi-simpledb` | 5 项通过，10.541 秒 | 5 项通过，11.017 秒 | 代码存在接口与实现参数约束，但编织日志为 0 个切点，不能据此证明 `MethodValidator` 行为 |
| `jcabi-w3c` | 9 项通过，21.415 秒 | 9 项通过，7.864 秒 | 覆盖不可变与重试切面，不直接覆盖验证异常分支 |
| `jcabi-maven-plugin` | 5 个集成场景通过，179 秒 | 5 个集成场景通过，120 秒 | 三个夹具各运行 2 项测试，约束异常断言证明 `MethodValidator` 相邻路径实际执行 |

随后为 `jcabi-maven-plugin` 的两个版本分别使用独立消费者副本、独立 Maven 本地仓和独立嵌套构建仓执行 `mvn clean verify -B`。0.22.2 用时 14 分 05 秒，0.22.3 用时 14 分 40 秒；两臂均通过 5 个集成场景，`ajc` 场景各运行 2 项测试且日志明确取得对应版本发布物。这排除了共享依赖缓存制造假绿，但现有测试只执行普通 `@NotNull` 约束，没有直接触发 `HV000151` 分支。

后续覆盖审计推翻了这一初判：四仓都没有触发 `HV000151` 分支，因此 0.22.2 到 0.22.3 不能作为 A3。替代候选 0.20.1 到 0.20.2 的八条双臂命令都通过，但真实 `ImmutabilityChecker` 变化方法只被 SimpleDB 覆盖，另外三仓没有进入变化类，同样被拒绝。当前四仓闭集不再搜索普通绿色版本对，完整评估见 `workstreams/jcabi-a3-repair/ASSESSMENT.md`。

### 正式重复结果

### 当前决定

### Jadler 破坏与恢复

固定 Jadler 2022-07-15 的基线代码并使用 Java 8 原生命令 `mvn clean test -B` 的单次筛选结果为：

| 臂 | SLF4J | Logback | 结果 |

| A2 | 2.0.0 | 1.3.4 | 六个模块共 389 项测试通过 |

A1 日志明确说明 SLF4J 2 忽略面向旧接口的 Logback 1.2.11 绑定，随后回退到 `NOPLoggerFactory`；五个错误均是测试把它转换为 `LoggerContext` 时失败。A2 只把 Logback 更新为 1.3.4，同一签名消失。

### 两个限定负例与一个未知仓

Password4j 的 1.7.36 与 2.0.0 两臂各执行 206 项测试并通过。测试确实进入 `PropertyReader` 和 `AlgorithmFinder` 等会调用 SLF4J 的路径，但两个版本都没有日志提供方，分别回退到旧式静态绑定缺失和新版无提供方的空实现。标签只能写成“无日志实现、该原生命令范围内无需修改”。

Spotless 的 `:lib:test` 实际没有测试，已作废。筛选阶段改用 `:testlib:test` 后，两臂各执行 155 项测试、跳过 7 项并通过；其中 `FreshMarkStepTest` 和 `SortPomTest` 进入使用 `LoggerFactory` 的生产路径。`spotless-lib` 明确要求没有运行时依赖，SLF4J 在两个相关源集都是仅编译依赖。因此它支持编译与这些格式化路径的限定负例，不支持任意日志提供方组合。

Spotless 首轮旧版本测试出现与 SLF4J 无关的 Gradle 内嵌依赖缓存写入失败。根因是容器用户未映射时 Java 把 `user.home` 推导为 `?`；固定到可写目录后，同一代码与命令的 155 项测试通过。另一次首次解析失败落在 Flexmark 的 PDFBox 父 POM，也被保留但不计入 SLF4J 结果。

RabbitMQ JMS Client 的 1.7.36 与 2.0.0 两臂各执行 114 项测试并通过，但 A1 明确报告 Logback 1.2.11 的旧绑定被忽略并回退到空实现。日志行为已经退化，只是当前测试没有判定它。把该仓标成负例会惩罚正确发现提供方不兼容的系统，因此当前标签必须是未知；后续应核对升级 Logback 是否构成目标修复。
