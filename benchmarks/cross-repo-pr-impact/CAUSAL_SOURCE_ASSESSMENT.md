# 因果执行证据来源评估

评估日期：2026-08-24

## 目的

本文件判断哪些公开执行系统能够为“跨仓破坏影响发现旗舰轨道”提供可核验样本。判断标准不是能否找到跨仓链接或失败记录，而是能否恢复下面这条证据链：

1. 源变更进入执行环境前，任务在旧组合上通过；
2. 只引入源变化后，同一任务出现与该变化相符的失败；
3. 保持源变化不变，只替换目标仓提交后，同一任务恢复；
4. 三次执行的仓库提交、时间、日志和任务身份都能独立核对。

现有 Zuul 两臂对照在源补丁代码相同、失败臂不含目标修复、成功臂实际含目标修复，并通过失败语义复核时也可接收。三臂结构的价值是额外证明“源变化引入失败”，而不只是“目标变化与恢复同时发生”。普通依赖声明、跨项目流水线关系、绿色构建或先失败后成功都不是标签。

## 总体判断

| 来源 | 确切提交 | 失败日志 | 恢复对照 | 目标修复归因 | 已执行负空间 | 长期可得性 | 当前决定 |
|---|---|---|---|---|---|---|---|
| OpenDev Zuul | 执行清单可得时强 | 可得时强 | 同任务两臂 | 语义复核后强 | 只覆盖执行组合 | 旧归档缺失严重 | 当前因果核心，改为滚动采集 |
| Kubernetes Prow | `clone-records.json` 强 | 公开对象存储 | 时间序列可构造 | 90 天试采未找到语义成立的配套修复 | 同任务历史可用 | 约 90 天归档完整 | 定向滚动线索，不作主体 |
| Rust Crater | 工具链与被测版本明确 | 报告和逐项日志完整 | 编译器前后两臂 | 偶有下游修复，通常无修复后重跑 | 很强 | 抽查归档完整 | 单列版本化生态破坏子轨 |
| BreakBot/Maracas | 源合并请求明确 | 无客户端执行日志 | 无 | 只有静态破坏用法 | 可生成静态未命中项，不是执行负例 | Zenodo 工件可得 | 作为源变化与客户端修复挖掘框 |
| FSE 2024 行为破坏数据 | 依赖版本明确，仓库修订缺失 | 客户端测试与日志可得 | 旧版本到破坏版本两臂 | 无维护者修复映射 | 未提供完整未失败集合 | Zenodo 工件可得 | 作为执行失败与后续修复挖掘框 |
| GitLab 多项目流水线 | 父、子流水线提交明确 | 取决于项目权限 | 无统一重试配对 | 无标准修复关系 | 仅限可见任务 | 项目差异大 | 暂不作为主体 |
| GitHub Actions | 当前仓 `head_sha` 明确 | 公共仓最长 90 天 | 无统一跨仓组合 | 依赖项目自定义协议 | 弱 | 不适合历史积累 | 拒绝作为通用历史来源 |
| Debian autopkgtest | 包版本明确 | 公开结果和日志 | 可观察触发包与反向依赖 | 映射回仓库 PR 困难 | 强 | 公共服务可再采 | 保留为包级备选 |

“已执行负空间”只表示某个候选确实在相同实验中运行且没有出现目标失败，不自动证明它在所有环境下都不受影响。

## OpenDev Zuul

### 已测储量

从 1055 个链独立源变更和 1525 个唯一目标变更中得到 286 个“同任务先失败、增加依赖后成功”候选。执行组合核验结果为：

- 4 个组合可确认；
- 198 个因历史 `zuul-info/inventory.yaml` 不可取得而无法判断，占候选的 69.2%；
- 84 个因多目标混杂、源代码变化、同仓或成功臂未采用目标修复而明确排除；
- 4 个组合确认项经失败语义复核后最终接受 2 个；1 个不稳定任务和 1 个外部环境变化被排除。后者初次接受后经重新复核降级，避免把与源差异无关的 Rocky 镜像密钥变化当作跨仓影响。

首个近期滚动窗口查询 2026-08-20 之后的记录，覆盖 106 个变更和 48 个项目。窗口内 4 个依赖转换中，3 个通过结构核验、共对应 5 个任务，执行清单均可取得。逐任务语义复核只接受 neutron→neutron-tempest-plugin 的固定版本测试适配；两个 Rally 任务实际失败于无关依赖解析，另两个任务修复外部 Ceph 仓库或 Rocky 镜像变化。滚动窗口的接受产率为 1/5 个结构通过任务，且原始搜索框、排除记录和语义决定均已保存。

随后将窗口扩大到 2026-08-01 之后，共覆盖 394 个变更、113 个项目和 20 个窗口内依赖转换。11 个转换、27 个任务通过结构核验；其中 5 个转换、7 个任务与此前记录重复。对余下 6 个转换、20 个任务逐项复核后，接受 3 个转换和 5 个任务：Magnum 并行节点组触发资源名称长度修复，Ironic Python Agent 新依赖触发共享要求登记，OpenStack SDK 新字段触发命令行客户端输出适配。另 15 个任务因外部 Git 或镜像故障、既有用户等待超时、依赖解析、包哈希或与目标补丁无关的功能失败而拒绝。完整搜索框、结构证据、逐任务决定和重复标记保存在 `results/opendev-rolling-2026-08-01-to-2026-08-23/`。

### 判断

Zuul 的优势不是 `Depends-On`，而是任务执行清单能够证明每个仓库实际检出的提交。历史归档缺失使它不适合一次性回挖到数百条，但近期记录仍是目前最贴合旗舰任务的来源。

后续应滚动检查新出现的相邻补丁集和同任务状态变化，在归档仍可用时立即保存结构化执行组合、失败签名和原始地址。无需保存海量原始日志；若原始日志失效，结构化摘要不能独立替代当时未核验的语义证据。

## Kubernetes Prow

### 公开结构

Prow 的任务定义支持 `extra_refs`，执行归档同时提供 `prowjob.json`、`build-log.txt` 和 `clone-records.json`。任务对象里的分支声明本身没有固定提交，但 `clone-records.json` 记录了每个实际克隆仓库的 `final_sha`，因此应以执行记录而不是任务配置作为组合真值。

2026-08-23 对 Deck 当前窗口的只读测量得到：

- 24,609 条任务；
- 3,844 条涉及至少两个不同仓库，其中 608 条为 PR 预提交任务；
- 3,176 条成功、387 条失败、215 条中止、6 条错误、60 条等待执行；
- 任务对象中没有一条多仓记录预先填全所有仓库提交，但运行时执行记录可以恢复。

一个公开周期任务的实测归档同时恢复了：

- `kubernetes/kubeadm`：`5bc6d39ca9ad65a5dc549dc388c80894044cf9af`；
- `kubernetes/kubernetes`：`e81f39c0e03ce8ed8e2660c9147b391edd9e262b`；
- 完整构建日志、测试报告和任务起止时间。

### 当前窗口试采

从 10 个同时包含成功和失败的多仓任务中核对 334 次执行，334/334 的 `clone-records.json` 均可取得。相邻执行中共有 23 个“成功、失败、成功”窗口：

- 20 个窗口在成功到失败之间没有任何仓库提交变化；
- 20 个窗口在失败到恢复之间没有任何仓库提交变化；
- 3 个窗口在恢复前恰有一个仓库变化，其中 2 个窗口在失败前没有代码变化，属于明显的不稳定任务候选；
- 另 1 个窗口在失败前后都只变化 `kubernetes/kubernetes`，但三次执行来自不同 PR，不是跨仓配套修复；
- 严格的“只改源仓后失败、只改另一个目标仓后恢复”三臂候选为 0。

### 约 90 天预提交历史

继续从 2026-08-23 当前配置中取出 104 个多仓预提交任务名，并遍历公开任务目录。目录覆盖 2026-05-26 至 2026-08-23，共 35,811 条记录，其中 35,805 条可解析状态和主仓提交：成功 22,717、失败 5,387、中止 7,617，其余 84。

按“同一任务、同一主仓合并请求”重组后得到 9,635 组，其中 1,960 组同时有成功和失败，包含 1,090 个相邻“成功、失败、成功”窗口。逐层收紧结果为：

- 299 个窗口的源合并请求头提交先变化后保持不变；
- 其中 58 个窗口同时保持源仓基提交不变，需要核对 174 次执行；
- 174/174 个 `clone-records.json` 可取得；
- 11 个窗口在失败前只有源仓变化、恢复前只有另一个仓库变化，来自 6 个唯一源合并请求；
- 核对 Git 代码树后，8 个窗口的两个源提交实际指向相同代码树，只是提交标识变化；
- 余下 3 个窗口分别是外部网络不可达、DRA 测试失败但目标差异不含对应修复，以及整套节点测试超时但目标只改了无关的 Kops 任务配置；
- 通过失败语义与目标修复语义复核的因果案例为 0。

完整漏斗在 `results/prow-three-arm-scan-2026-08-23.json`，11 个结构候选和逐项决定分别保存在 `candidates/prow-three-arm-structural-candidates.jsonl` 与 `candidates/prow-three-arm-semantic-review.jsonl`。

### 判断

Prow 的证据保存质量明显优于当前 OpenDev 历史归档，但通用历史挖掘的语义产率为 0/35,805。它不再作为旗舰主体来源，只保留为定向滚动线索：优先监测项目讨论中已经出现配套修复关系的任务，再核对三臂。筛选必须比较 Git 代码树而不是提交号；强推、变基或只改提交元数据不能算源代码变化。“失败后另一仓有新提交”仍不能升级为目标修复。

## Rust Crater

### 公开结构与可得率

Crater 对两个 Rust 工具链运行同一批 crates.io 版本和 GitHub 提交，并生成 `config.json`、`results.json`、分类报告、重试列表和逐项日志。报告明确记录起始与目标编译器提交、实验模式和时间。

对 GitHub 搜索得到的 20 个近期活跃、已有完成实验的 Rust PR 做可得性试采：

- 20/20 个选定实验的汇总报告仍可访问；
- 其中 17 个有根因回归，分别抽取一条失败日志，17/17 仍可访问；
- 报告中可直接恢复被测 crate 版本或 GitHub 仓库提交，以及前后工具链提交；
- 3/20 个源 PR 的讨论能够逐项还原出 4 个直接源码修复候选。此前“5 个目标”的试采计数没有留下可逐项审计的清单，现不再沿用。4 个候选已固化到 `candidates/crater-linked-fix-candidates.jsonl`，现均已完成原工具链三臂；其中 1 个以下游依赖方而不是两臂均失败的根包为执行对象。

`rust-lang/rust#155193` 已补成第一条完整三臂。原报告证明 `spectest-0.1.2` 在基准编译器通过、在目标编译器以 `E0539` 失败；`aalexandrov/spectest#1` 只把两处非法的 `#[inline(always = true)]` 改成 `#[inline(always)]`。本地以同一依赖锁文件和原 `cargo check --frozen --all --all-targets` 命令分别执行“基准编译器加原版本”“目标编译器加原版本”“目标编译器加精确修复”，每臂使用独立构建目录重复 3 次，结果稳定为通过、失败、通过，失败签名与原报告相同。

该重放仍有两个明确差异：2026 年 8 月重新解析的依赖闭包有 56 个包，而原实验日志记录 84 个；原容器摘要在限定时间内没有拉取完成，因此本地三臂运行在宿主机。依赖锁文件在本地三臂间保持完全相同，且失败是编译器对目标源码属性的直接诊断，所以这两项不推翻恢复归因，但该结果应表述为“版本化包的因果恢复已确认，原 Crater 环境并非逐字节复刻”。完整记录见 `results/crater-replay-pr-155193-2026-08-23.json`。

`rust-lang/rust#154992` 与 `git-url-parse-0.6.0` 是第二条完整三臂。发布包自带 74 包锁文件，原 Crater 日志确认没有重新生成；目标编译器稳定复现 `E0038/E0271/E0599/E0631`，只把 `tjtelan/git-url-parse-rs#84` 修改的 `src/types/spec.rs` 应用到发布包后稳定通过。三臂同样各完成 3 次有效重复。该修复 PR 在重放时仍未合并，所以证据证明“修复有效”，不证明“维护者已经采纳”。准备阶段还保留了依赖未预取和命令参数误写两类编译前失败，它们不计入有效重复。完整记录见 `results/crater-replay-pr-154992-2026-08-23.json`。

`rust-lang/rust#156776` 与 `id3-1.16.4` 是第三条完整三臂。发布包自带 58 包锁文件，目标编译器稳定复现 `E0521`；只应用 `polyfloyd/rust-id3#162` 头提交相对其父提交的一行生命周期修复后稳定通过，三臂各重复 3 次。该 PR 分支已经落后于当前目标分支，直接比较当前基线与头提交会混入工作流、版本和其他源码回退，因此恢复干预必须取提交相对父提交的差异。完整记录见 `results/crater-replay-pr-156776-id3-2026-08-23.json`。

`bevy_channel_trigger-0.6.0` 线索已经以下游依赖方补成第四条三臂。原报告中根包在两个编译器臂都因 `ash` 或 `syn` 失败，不能构成对照；因此固定同一报告中从通过转为依赖失败的 `bevy_ios_app_delegate-0.4.0` 及其发布包锁文件。基准工具链 3/3 通过，目标工具链 3/3 在 `bevy_channel_trigger` 的同一位置报“生命周期必须长于 `static`”，只把该依赖替换为 `rustunit/bevy_channel_trigger#3` 的精确修复提交后 3/3 通过。151 个解析包中其余 150 个不变。该修复已经以等价提交进入主分支；完整记录见 `results/crater-replay-pr-156776-bevy-ios-app-delegate-2026-08-23.json`。

这 20 个实验的漏斗现在可以给出有限但明确的产率：3/20 个源 PR 暴露 4 个可逐项审计的直接修复，4/4 经人工恢复后通过受控重放。前者说明自然出现并可追溯到具体修复的线索稀少，后者说明一旦有高质量线索，三臂补证成功率高。它适合作为小型高强度版本化生态子轨，不足以单独扩成数百条仓库级旗舰数据。

### 任务本体差异

Crater 的标签单位首先是“发布的 crate 版本或固定 GitHub 提交”，不一定等于观察截止时目标仓默认分支。例如 never type 变化导致大量旧 Redis 依赖版本失败，但 Redis 主仓早在该源 PR 出现前已经修复。如果输入使用目标仓当时默认分支代码，系统会看到已修复代码，而标签仍指向旧包版本。

因此 Crater 不应混入现有相邻仓配套修复分数。它适合单列为“版本化生态破坏发现”子轨：输入必须是实验实际执行的包版本或仓库提交；其大规模同实验未回归项可以形成执行负空间。具体案例只有补做同工具链、同命令的目标修复重放后才能升级；目前 4 条已达到该标准，但不能据此证明其他修复都可恢复，也不能代表仓库默认分支影响。

## BreakBot/Maracas 静态影响框

BreakBot 的公开工件 DOI 为 `10.5281/zenodo.7475823`，`data.csv` 保留了 230 个 Java 源仓的 3786 个合并请求分析记录。对原始 CSV 用结构化解析器重算得到：

- 83 个源合并请求至少命中一个静态破坏客户端；
- 这些记录来自 37 个唯一源仓；
- `brokenClients` 字段累计 481 个客户端命中；
- 全表 `checkedClients` 字段累计 17408 次客户端检查。

这些数字只表示 Maracas 在客户端源码中找到了与 API 变化匹配的破坏用法。平面 CSV 没有保留客户端测试失败、修复提交或完整客户端身份清单；采集时的合并请求状态也不等于当前已合入。因此 83 个源变化都不能直接进入标签。

下一阶段只将它用作高密度挖掘框：恢复源合并请求的基提交与头提交，重建被命中的客户端列表，再在每个客户端的后续历史中寻找精确维护者修复。只有 A0、A1、A2 真实执行成立后才进入因果候选。静态未命中的客户端不作负例，限定负例仍需证明变化表面进入实际执行合同。

## FSE 2024 行为破坏数据

FSE 2024 论文《Understanding the Impact of APIs Behavioral Breaking Changes on Client Applications》的 Zenodo 工件保存了 Maven 依赖升级后的真实客户端测试结果。无需下载 9.96 GB 虚拟机，远程 ZIP 目录中的两个去重工作簿可以单独取得。结构化读取 `Test_Failure_Data.xlsx` 与 `Test_Errors_Data.xlsx` 得到：

- 425 条去重断言失败记录和 618 条去重异常失败记录；
- 按依赖坐标、当前版本、破坏版本、客户端制品和仓库目录提示聚合后为 703 个依赖升级候选；
- 候选涉及 323 个依赖坐标、471 个客户端制品和 483 个客户端目录提示；
- 304 个候选有断言失败，457 个有异常失败，其中 58 个同时具有两类失败。

这批证据比静态破坏用法更接近旗舰任务，因为论文实验确实在客户端上替换依赖并运行测试，工作簿还保留测试方法、失败日志、Java 版本和依赖作用域。其缺口也同样明确：工作簿没有精确的源仓与客户端仓修订，没有维护者修复提交，也没有可直接作为限定负例的完整未失败客户端清单。`Directory` 只能帮助恢复仓库和模块，不能代替修订身份。破坏版本还可能包含多个源提交，而 Marshal 的输入单位是单个拉取请求；正式准入前必须把行为变化继续隔离到一个源提交或拉取请求。

因此 703 个条目只进入执行失败搜索框。后续按同一源版本影响多个客户端的关系族排序，先恢复源版本提交、客户端历史修订和维护者后续修复，再执行 A0、A1、A2。只有三臂成立的条目才进入因果候选；A3 与限定干扰仓仍需另行寻找和执行。可再生提取器为 `collect_fse2024_behavioral_candidates.py`，完整聚合框和统计分别保存在 `candidates/fse2024-behavioral-breakage-frame.jsonl` 与 `candidates/fse2024-behavioral-breakage-metadata.json`。

首个 PowerMock 1.6.4 到 1.6.5 关系族验证了这条准入纪律的必要性。ViSearch 的 A1 能复现论文记录的报告器缺失异常，但维护者真实提交只删除没有代码的聚合依赖，A2 仍以同一异常失败；目标严格 A0 还因 Maven Central 从未提供其声明的聚合 JAR 而无法直接解析。恢复环境只用于诊断公开失败签名，不能替代严格三臂。该关系接纳 0 条，其余七条同源同签名记录在没有独立维护者修复前保持未知。

第二个 H2 1.4.199 到 1.4.200 关系族则产生了正向产率。精确源提交 `92692e63` 删除 `MVCC` 连接设置，在 1.4.199 其余代码不变时即可复现错误码 `90113`。Database Rider 与 CloudSlang Score 的原生测试都完成通过、失败、只删除 `MVCC` 后恢复的三臂。公开五条记录中四条只是 Score 的两个模块和仓库别名，故按根仓折叠为两个独立正关系，而不是五条。当前仍没有可判定负例或 A3，不能从两条正关系提升为完整项目包。

JUnit 4.11 到 4.12 的八仓筛选在执行前停止：七仓没有维护者恢复，PIT 只有一条 2023 年未重放修复线索。五个 PowerMock 客户端的字段错误也不能归到虚构的单次字段改名；真实 JUnit 历史是先删除 `MethodValidator`，再做全仓字段风格迁移，最后按新字段名恢复该类。该家族接纳 0 条，PIT 只保留单仓后续线索，其余仓继续保持未知。

JAX-RS 2.0.1 到 2.1-m08 的八条目录记录经关系去重后只有两个根仓：Fastjson 一条、Microbule 七个模块共用一条。源破坏可以精确隔离到 `79bd5309`：它给 `ResponseBuilder` 新增抽象 `status(int, String)`，使按旧接口编译的 CXF 实现在运行时产生 `AbstractMethodError`。但 Fastjson 与 Microbule 的历史都保持 JAX-RS 2.0.1 和旧 CXF，没有维护者精确 A2；模块扩散不能替代独立恢复关系。因此该家族在执行前接纳 0 条，固定旧版本与停止维护也不作负例。

## GitLab 多项目流水线

### 项目与流水线可见性

对 9 个公开 GitLab 项目检查流水线接口：`gitlab`、`gitlab-runner`、`gitlab-foss`、官网、文档和命令行工具 6 个可访问；Omnibus、Charts 和性能项目 3 个返回 403。公开仓库并不保证流水线公开。

对 6 个可访问项目各取最近 100 条父流水线：

| 父项目 | 跨项目下游 | 失败 | 成功 | 其他状态 |
|---|---:|---:|---:|---:|
| `gitlab-org/gitlab` | 12 | 2 | 7 | 3 |
| `gitlab-org/gitlab-runner` | 83 | 54 | 29 | 0 |
| `gitlab-com/www-gitlab-com` | 84 | 0 | 84 | 0 |
| 其余 3 个可访问项目 | 0 | 0 | 0 | 0 |

共得到 179 条跨项目下游关系。Bridge 数据包含下游项目、流水线、提交、分支和状态，但这些字段只证明触发关系，不证明失败由父仓变更造成。

对其中 43 条按父项目和状态抽样核对任务与日志：

- 29 条可以公开列出任务；
- 9 条任务接口返回 403，均来自一个流水线不可见的下游项目；
- 5 条指向已经不可见或不存在的下游项目；
- API 日志端点对匿名请求返回 401，但对 4 个可见下游项目各抽一条成功或失败任务，网页日志端点 4/4 可分段读取。

在三个确有跨项目下游的父项目最近 100 条流水线中，没有找到“相同父提交、目标提交变化、下游由失败转成功”的记录；`gitlab-runner` 同一合并请求内也没有这种组合。

### 判断

GitLab 适合保留为滚动线索源，尤其是流水线和网页日志均公开的项目。当前没有可规模化的目标修复关系，也没有严格对照产出，优先级低于 Prow。若未来项目自行记录配套目标提交或出现同父提交重试对照，再按旗舰标准逐项核验。

## GitHub Actions

GitHub 官方文档规定，工作流日志和制品默认保留 90 天；公共仓最长也只能设置为 90 天。工作流运行接口提供当前仓库的 `head_sha`，但没有标准字段列出任务实际使用的其他仓库提交。

项目可以在工作流脚本中自行检出其他仓库，也可以上传自定义清单，但这不是平台统一协议。它既不适合作为长期历史主体，也不能从通用接口稳定恢复跨仓组合。只有明确保存多仓提交和失败到修复对照的具体项目，才值得单独纳入。

## Debian autopkgtest

Debian 持续集成服务按触发包版本运行其他源码包声明的 `autopkgtest`，能够提供真实反向依赖执行和日志。其优势是执行负空间自然存在，缺点是任务单位为包版本，不是源仓 PR；同一包还可能来自与上游仓不同的打包仓。

在没有稳定的“上游 PR、Debian 源包版本、目标修复 PR”三方映射前，它不进入当前旗舰轨道。若以后建设包级影响评测，可重新评估，不能把包版本标签直接改名为 PR 影响标签。

## 来源路线

1. 持续滚动采集 OpenDev 新对照，趁执行清单和日志尚可访问时完成组合与语义核验。
2. Prow 的约 90 天预提交历史已完成扩大试采，35,805 次执行中没有语义成立的三臂案例。停止把通用 Prow 历史作为主要候选来源，只对已有配套修复线索的项目做滚动核验。
3. 将 Crater 设计成独立的版本化生态破坏子轨，并选择少量目标修复明确的案例做同工具链恢复重放；重放前不升级为完整因果案例。
4. 从 BreakBot 的 83 个静态正命中源变化中按仓库去重挖掘客户端后续修复，但不将静态命中或未命中改写为执行标签。
5. 从 FSE 2024 的 703 个执行失败候选中优先恢复多客户端关系族；仓库修订和维护者修复未恢复前不生成标签。
6. GitLab 只监测流水线、任务和网页日志均公开的项目，不因 Bridge 状态直接生成标签。
7. GitHub Actions 和 Debian autopkgtest 暂不投入主体采集，除非发现满足各自缺口的具体项目协议。

上述调查改变的是来源优先级，不降低 `TASK_DEFINITION.md` 的因果准入条件，也不改变现有 6 条 Zuul 因果储备的独立盲复核要求。
