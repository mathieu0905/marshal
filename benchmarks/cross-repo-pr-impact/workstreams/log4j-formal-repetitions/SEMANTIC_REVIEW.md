# Log4j 项目包独立模型语义复核

复核日期：2026-08-25

## 结论

有条件接受该项目包进入“模型质检通过、待第二位人工盲复核”层。可接受的任务单元不是“Log4j 2.18.0 会破坏哪些仓库”，而是以下限定合同：

- 源输入是 `log4j-core` 2.17.2 到 2.18.0，同时目标仍解析 `log4j-api` 2.17.2；
- 正目标 `equinor/neqsim` 需要把 API 配对到 2.18.0，才能恢复同一原生测试合同；
- 三个限定负例按各自真实版本管理方式同步消费 API 与 Core，在选定原生测试合同内不需要额外目标修改；
- A3 只证明 2.17.1 到 2.17.2 的同步变化在四仓已覆盖路径上兼容。

这是一条多制品版本协调关系，不是任意 Log4j 源码变化、任意模块替换或完整生态影响面的标签。

## 正例核对

Neqsim 的三个历史提交构成同一维护链：A0 同时使用 API/Core 2.17.2，A1 只把 Core 升至 2.18.0，A2 再把 API 配对至 2.18.0。A1 三轮均运行 134 项测试并出现 131 个错误，稳定命中缺失 `ServiceLoaderUtil`；A0 与 A2 三轮均为 180 项通过。A2 是维护者合并的配对版本变化，不是数据集作者编写的恢复补丁。

该标签只能写成“需要协调上游同仓发布物的版本声明”。两个版本更新由自动化工具生成并不削弱提交历史真实性，但也不能把它叙述成维护者先诊断接口错误、再设计代码修复。

## 限定负例与兼容控制

`archifacts/archifacts`、`elimu-ai/webapp` 和 `aws-powertools/powertools-lambda-java` 的 A1/A2 输入逐仓相同，完整 Log4j 依赖图也逐轮相同且非空。前置覆盖筛选命中 Core 2.18.0 调用新增 API 的变化面，因此这些绿色结果不是完全未执行相关路径。

负标签仍受命令范围限制。Powertools 只有 3 项结构化日志定向测试；其余两仓虽运行完整 Maven 测试，也不能外推到未启用的追加器、部署方式或异步路径。它们证明的是同步消费时无需额外目标协调，不是“仓库不受 Log4j 影响”。

A3 的四仓前后臂三轮均通过，前置覆盖证据共同命中初始化变化路径。它只充当真实兼容变化控制，不证明 2.17.2 到 2.18.0 的所有其他变化兼容。

## 剩余边界

- 当前闭集是按已恢复失败线索和有变化面覆盖的干扰仓构造的四仓评测目录，不是 Log4j 生态的完整影响集合。
- 正例的因果机制是同一上游仓库中 API/Core 发布物错配，报告必须保留多模块源仓这一条件。
- 三次正式重复没有重新插桩；变化面判断仍来自正式重复前的独立覆盖筛选。
- 本文件是未参与执行的模型语义复核，不是第二位人工标注者的盲复核。

在上述标签上限下，方向、机制、维护者恢复、限定负空间和兼容控制相互一致，模型质检接受。
