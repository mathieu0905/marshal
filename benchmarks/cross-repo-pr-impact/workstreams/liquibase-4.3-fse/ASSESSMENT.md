# Liquibase Core 4.2.2 到 4.3.0 的 FSE 关系族筛选

更新日期：2026-08-25

## 结论

FSE 2024 的完整精确版本框只有 2 条候选，来自 `CloudSlang/score` 与 `adorsys/datasafe` 两个独立根仓。两个公开执行都在原生数据库测试中命中同一异常：`HubUpdater.register` 第 306 行对空的 `HubService` 调用 `isOnline()`。

这是一组很强的执行线索。4.2.2 到 4.3.0 是按提交链向前的真实发布变化，精确源提交与官方修复也都能定位。但是两个目标仓的完整历史都没有采用固定的 4.3.0，也没有维护者在 4.3.0 下作出恢复。它们在 2022 年直接从 3.x 跳到已经包含上游修复的 4.8.0。

因此本轮正式接纳 0 条，未做本地 A0/A1/A2 重放，也没有限定负例或 A3。两条记录保留为“一个精确源缺陷击中两个独立根仓”的高质量机制锚点，不能冒充具有消费仓维护者 A2 的正式因果正例。

## 完整候选框

| FSE 候选 | 根仓 | 原生测试 | 完整异常的根因 |
|---|---|---|---|
| `0567` | `CloudSlang/score` | `WorkerLockRepositoryTest.deleteByUuidTest` | Spring 创建 Liquibase 时，`HubUpdater.register:306` 空指针 |
| `0568` | `adorsys/datasafe` | `DatabaseStorageServiceTest.objectExists` | 数据库结构更新时，同一行空指针 |

`openscore/score` 是历史地址，当前会重定向到 `CloudSlang/score`。它不是额外根仓。两条候选的模块、维护历史和 Git 主键均不同，因此这里确有两个独立消费仓，而不是模块拆分。

## 精确源机制

4.2.2 标签解引用到 `a5a01b5d...`，4.3.0 解引用到其后代 `c6ca2a5d...`。源变化方向有效。

行为起点是 `e315881f...`。该提交把原有的在线与离线 Hub 服务替换为 `StandardHubService`，并在构造时创建 `HttpClient`。`HttpClient` 直接引用 SnakeYAML；目标类路径没有 SnakeYAML 时，插件无法实例化，而 `HubServiceFactory.getService()` 当时会返回空。随后 `HubUpdater.register` 在第 306 行直接调用 `hubService.isOnline()`，形成两个工作簿记录中的同签名异常。

Liquibase 自己在 `e92af870...` 明确以“Liquibase 4.3.0 在类路径缺少 SnakeYAML 时抛空指针”为题修复 LB-1212，并由 `8cf38a98...` 合入：工厂找不到标准服务时返回离线后备实现。该修复进入 4.3.1 及以后版本，不属于消费仓在固定 4.3.0 下的 A2。

## 目标历史审计

### Score

完整远程引用共有 4622 个可达提交。对每个不同的根 POM 内容作结构化解析后，Liquibase 版本分布包含 3.4.2、4.8.0 和更晚版本，4.3.0 为 0。

`d135af3c...` 是首次后续采用，只把 3.4.2 升到 4.8.0。它使用的是已经修复 LB-1212 的新源输入，不是维持 4.3.0 的目标修复。

### Datasafe

完整远程引用共有 2159 个可达提交。根 POM 的结构化历史同样没有 4.3.0：维护者由 3.6.1 直接升到 4.8.0，提交为 `ada0fa6a...`。

`633ec765...` 后来确实修改了数据库字段引用，但对应 Liquibase 4.23.1 与 H2 2.x 的关键字合同，和 4.3.0 的 Hub 服务空指针无关，不能借用为 A2。

## 为什么不重放

公开工作簿已经保存了两个 A1 的完整原生异常，但没有保存目标 Git 修订。更重要的是，完整维护历史中没有固定 4.3.0 的 A2。选择一个版本匹配的目标提交、人工加入 SnakeYAML，确实可能构造 A0 通过、A1 失败、A2 通过；普通测试也能验证这个人工方案。但它只能证明作者知道官方缺陷的规避方式，不能证明消费仓维护者曾作出这项修复。

另一个容易误标的做法是把 4.8.0 一行升级当成 A2。这样恢复来自上游已经改变的源输入，不再是固定 A1 变化下的目标恢复，违反三臂的因果隔离。

## 证据边界

本组证明的事实是：Liquibase 4.3.0 的 LB-1212 缺陷在两个独立消费仓的真实数据库路径中被执行并产生同签名失败。它不证明两个消费仓存在维护者 A2，也没有精确目标修订、限定负例或兼容变化 A3。

机器可读候选、根仓裁决和历史证据分别位于 `candidate-frame.jsonl`、`root-audit.jsonl` 与 `history-evidence.json`；紧凑结果位于 `results/liquibase-4.3-fse-history-screening-2026-08-25/summary.json`。
