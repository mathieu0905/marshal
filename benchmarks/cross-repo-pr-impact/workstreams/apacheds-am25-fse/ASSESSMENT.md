# ApacheDS 2.0.0.AM25 关系族筛选结论

## 结论

本关系族不接纳为旗舰因果项目包。

- 完整候选框共有 3 条，全部是 `org.apache.directory.server:apacheds-all` 从 `2.0.0-M24` 替换为 `2.0.0.AM25` 后出现的同一种签名校验异常。
- `0321` 与 `0322` 是同一个 `ctco/cukes` 仓库的历史名称重复；加上 `SonarSource/sonar-ldap` 后，实际只有 2 个独立根历史。
- 源端存在单一提交中的明确机制，并已用 Maven Central 的真实发布成品执行确认。
- 两个客户端根历史均没有接受过 AM25，也没有维护者提交在保持 AM25 的前提下删除无效签名元数据或绕过同一失败机制。
- 因精确 A2 为 0，按既定准入标准不执行客户端 A0/A1/A2 重放；本关系族产出 0 个可接纳案例。

## 根历史去重

GitHub 接口对 `ctco/cukes-rest` 与 `ctco/cukes` 都返回仓库编号 `45254631`，因此 `0321` 与 `0322` 是同一仓库迁移历史中的重复观测。

`SonarCommunity/sonar-ldap` 当前解析为已归档的 `SonarSource/sonar-ldap`，仓库编号为 `4673630`。

## 源机制

源仓为 `apache/directory-server`。相关标签是：

- `2.0.0-M24`：`049ab3b8a7a5be4516fd964ad595147bab7e42df`
- `2.0.0.AM25`：`40ab08d93c6125ccb59d692b25759361307195d3`

两个发布标签不在同一祖先链上，不能把整个标签差异当作线性源改动。提交 `6200fa2b25e9aa96517283dd9a965a753eeca7b1` 只把 `bcprov-jdk15on` 从 1.56 升到 1.59；它属于 AM25 标签而不属于 M24 标签。1.59 改变了签名文件名称，而 `apacheds-all` 的合并包过滤仍只删除 1.56 的旧名称，导致 AM25 成品保留与重写后清单不匹配的签名文件。精确一行改动见 `source-mechanism.patch`，成品测量见 `MECHANISM_PROBE.md`。

## 精确 A2 审计

对两个客户端根历史的全部可达引用进行依赖版本、签名过滤和失败测试路径审计：

- `ctco/cukes` 在 `0a741a4d...` 引入 LDAP 示例时固定使用 M24；后续测试框架升级与代码清理仍保留 M24。全部历史中没有 AM25，也没有签名过滤规则。
- `SonarSource/sonar-ldap` 的两条平行历史提交把 M23 升到 M24，结果树相同；后续 OpenJDK、许可证和 JUnit 变更仍保留 M24。全部历史中没有 AM25，也没有签名过滤规则。

该异常在 JVM 校验合并包签名时发生，早于客户端测试逻辑。仅更新测试框架或测试代码无法构成保持 AM25 的恢复；维护者必须改变依赖构成或清理签名元数据，但两个根历史中都没有这样的提交。

## 原始材料边界

FSE 表格提供了三次真实失败及测试名称，但不提供精确客户端 Git 修订。源机制已经成立，然而旗舰三臂仍要求维护者精确 A2；缺少 A2 时，下载虚拟机镜像只能帮助恢复 A0/A1 时点，不能制造不存在的维护者恢复。因此停止在筛选阶段。
