## 当前判断

Jackson 候选组已经恢复完整搜索框，并找到一组可继续筛选的统一变化：
`jackson-databind 2.10.5.1 -> 2.12.6.1`。这组目前有两个原生失败消费仓和两个同步版本管理的限定负例，但还不能提升为多正例旗舰项目包。两个负例的变化面和兼容控制已经完成覆盖证明；剩余缺口是第二个正例的维护者精确修复证据。详细覆盖判定见 `COVERAGE_ASSESSMENT.md`。

## 失败语义复核

### Splunk

PR 327 只把 Databind 从 2.10.5.1 升到 2.12.6.1。原生 `mvn clean test -B` 在 Java 11 下重放得到：

- 父提交 `374ef350...`：143 项测试全部通过；
- 变更提交 `55931d4c...`：143 项测试中 97 项错误；
- 主要签名是 `NoClassDefFoundError: com/fasterxml/jackson/core/util/JacksonFeature`，实际解析的 `jackson-core` 仍为 2.10.5。

维护者随后合并 PR 330（提交 `ddbd37d5...`），同时把 Core 升到 2.12.6、Databind 升到 2.12.6.1，并按新版本行为调整时间格式。本轮原生重放确认修复后 143 项测试全部通过，实际解析版本也与预期一致。这是同一基线上的真实协调修复，可作为 A2 候选。

### Dropwizard Pac4j

PR 272 同样只升级 Databind。原生重放确认父提交通过，变更提交因 `jackson-core:2.10.5` 与 `jackson-annotations:2.10.5` 的依赖收敛冲突失败。

但该 PR 的父提交是陈旧分支，仓库在此之前已经分别合并过更新 Dropwizard BOM 和 Jackson 的提交。人工把 Core、Annotations 与 Databind 对齐后，16 项测试可以恢复；直接把 Dropwizard BOM 更新到 2.0.28 则会引入多组新的依赖收敛冲突。没有找到维护者针对 PR 272 的精确修复。因此它目前只能作为“真实可重放失败候选”，不能与 Splunk 等强度计入正式正例。

## 限定负例候选

两个仓库都使用 Jackson BOM 同步管理组件版本，且原生测试直接执行 JSON 序列化路径：

| 消费仓与固定提交 | 2.10.5.1 | 2.12.6.1 | 测试量 |
| --- | --- | --- | --- |
| `spotify/github-java-client` `a63577cb...` | 通过 | 通过 | 96 |
| `tokuhirom/avans` `b987be9c...` | 通过 | 通过 | 69 |

前者通过 BOM `2.10.5.20201202 -> 2.12.6.20220326` 实际解析出目标 Databind 版本；后者同样解析到目标版本。依赖覆盖进一步确认两仓分别执行了 133/209 和 114/209 个变化生产类，并覆盖新增的 `BeanSerializerFactory.java:415` 调用点，因此可接纳为限定负例。

## A3 候选

最初的 `2.12.5 -> 2.12.6` 已淘汰：四仓只执行了新增判断的假分支，没有进入真正改变结果的分支。`2.12.3 -> 2.12.4` 也因没有四仓共同覆盖的新增可执行行而淘汰。

当前接受候选改为相邻次版本 `2.11.4 -> 2.12.0`。四仓前后臂全部通过，2.12.0 的新增生产源码中有 434 条新增可执行行被四仓共同覆盖，包括新增 `ConstructorDetector` 和创建器候选收集路径。它必须称为“相邻次版本兼容控制”，不能写成补丁版本控制。

## 接纳条件与下一步

1. 为第二个正例寻找维护者真实协调修复；若 Dropwizard 只能得到人工对齐，不把它提升为正式正例。
2. 在第二个正例出现前，将当前材料作为单正例锚点，不做三次正式重复来制造“已完成项目包”的观感。
3. 第二个正例成立后，再把已确认的两个限定负例和 `2.11.4 -> 2.12.0` 兼容控制写入正式隔离重复脚本。
