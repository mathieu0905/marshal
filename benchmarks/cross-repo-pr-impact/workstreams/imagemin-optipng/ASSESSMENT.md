# imagemin-optipng 到 images-to-less-variables 筛选

更新日期：2026-08-24

## 结论

这条关系形成一个可保留的独立三臂因果正例。`imagemin-optipng` 4.1.0 到 4.2.0 改变 OptiPNG 参数和默认优化级别，使同一张测试图片的压缩结果从 225 字节变为 228 字节；固定目标代码后，原生 8 项测试从全部通过变为 3 项失败。只应用维护者真实提交中对压缩长度和字节串的两处期望更新后，8 项测试恢复通过。

该正例属于“输出合同适配”，不是生产调用代码修复。复现包在这一源版本下只提供一个目标仓，当前没有限定负例。4.0.0 到 4.1.0 的单目标兼容控制进入了真实变化分支，但不能冒充多消费仓 A3 或完整项目包。

## 来源恢复

Zenodo 复现包 DOI `10.5281/zenodo.5558085` 的 64 条记录中，只有一条使用 `imagemin-optipng@4.2.0`：

- 顶层客户端和目标修复仓都是 `images-to-less-variables`；
- 复现包记录客户端从 0.0.3 到 0.0.5 恢复，修复类型为代码修改；
- 原始地址 `Brightspace/images-to-less-variables` 已失效，后来改名的 `Brightspace/images-to-variables` 也已删除。

Libraries.io 保存的迁移元数据仍指向新名称，并列出四个分叉。`omsmith/images-to-variables` 保留 53 个提交及 `v0.0.1` 到 `v0.3.2` 标签，完整包含旧名称、改名过程和目标修复。`brian-pearson` 与 `pdehaan` 的分叉也保留同一早期历史，因而不是由单个失效链接推测提交。

本轮固定 `v0.0.4` 的提交 `94da609777c4af78dc06bd9a0f773531ec0635e6` 作为目标基线。它相对复现包所列的 0.0.3 只改变版本号和 README 依赖徽章，生产代码与测试完全相同；使用更接近修复前一刻的 0.0.4 不改变故障合同。

## 三臂执行

执行环境为 Node.js 6.17.1、npm 2.15.12，目标原生命令是 `npm test`。所有臂固定同一目标提交和同一依赖种子，显式解析 `imagemin` 3.1.0；只有 `imagemin-optipng` 版本和 A2 的目标修改不同。

| 臂 | 源版本 | 目标修改 | 原生结果 |
|---|---:|---|---|
| A0 | 4.1.0 | 无 | 8 项通过，压缩结果 225 字节 |
| A1 | 4.2.0 | 无 | 8 项中 3 项失败，实际 228 字节、期望 225 字节 |
| A2 | 4.2.0 | 只应用维护者提交 `b3f8796d...` 的测试期望修改 | 8 项通过，压缩结果 228 字节 |

源提交 `1b2c2a54d51098501a5b581a2df4191d12dce15a` 删除 `-quiet`，增加 `-force` 与 `-fix`，并把默认优化级别从 3 改为 2。A1 的三个失败分别覆盖压缩变量值、带前缀变量值和写入 Less 文件的值，失败字节串与维护者提交记录完全一致。

目标提交 `b3f8796d8f78e09a4632277bea0bc709c7879b96` 的说明是“底层 imagemin 更新后修正期望结果”。它只把测试中的压缩长度从 225 改为 228，并替换对应的 Base64 字节串。本轮 A2 只抽取这两处修改，没有带入父提交里的 Chalk、Q、Vinyl FS 依赖升级，也没有手工发明恢复代码。

历史 Gulp/Jasmine 任务有一个需要明确处理的缺陷：即使 Jasmine 报告 3 项失败，进程退出码仍为零。因此机器摘要中的 `contract_result` 由 Jasmine 的失败计数产生，不能把退出码零解释为 A1 通过。原始日志保留了完整失败断言。

## 兼容控制

单目标控制使用 `imagemin-optipng` 4.0.0 到 4.1.0，同一目标代码和原生命令两侧均为 8 项通过。4.1.0 的真实源变化是“只有优化结果更小时才替换原图”。测试日志确认 477 字节输入被压缩为 225 字节，所以 `225 < 477`，后臂实际进入新增条件的真分支，而不是只加载了包。

这只能说明当前目标在该真实变化下兼容。来源搜索框没有第二个独立消费仓，故状态为单目标兼容控制，不计多仓 A3。

## 负空间

复现包中 `imagemin-optipng@4.2.0` 只有这一条客户端记录。没有另一个仓能够在同一源变化下执行压缩结果合同，因此本轮不产生限定负例。普通安装成功、未出现论文记录或随意选择一个图像工具的绿色测试，都不能证明其执行了 4.2.0 的参数与输出变化。

## 接纳边界

1. 这条关系计一个链独立三臂因果正例，标签类型必须写为输出合同适配。
2. A1 的判定依据是 3 项 Jasmine 失败及精确字节差异，不是进程退出码。
3. 4.0.0 到 4.1.0 只作单目标兼容控制，不计限定负例或多仓 A3。
