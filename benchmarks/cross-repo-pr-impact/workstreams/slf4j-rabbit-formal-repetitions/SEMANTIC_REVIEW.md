# SLF4J 到 RabbitMQ JMS Client 的独立语义复核

复核日期：2026-08-25

## 结论

RabbitMQ JMS Client 可以从“影响未知”改为**有边界的正例**，但标签必须写成：

> 在 RabbitMQ JMS Client 固定采用 SLF4J 2.0.0、并保留测试范围的 Logback 提供方这一配置意图时，Logback 1.2.11 不再被加载；把 Logback 更新到兼容 SLF4J 2 的 1.4.0 后，提供方初始化恢复。

它不能扩写为“SLF4J 2 破坏 RabbitMQ 消息功能”，也不能写成“RabbitMQ 项目长期采用了 SLF4J 2”。Logback 在该仓中是测试范围依赖，新增合同判定的是仓库测试环境里显式配置的日志提供方是否实际生效，不是发布制品在任意最终用户运行环境中的日志实现。

这项证据足以撤销原先把 RabbitMQ 当作负例的判断。它也足以把当前四仓集合描述为“两个正例、两个各自有明确上限的负例”。但不宜把四仓包装成同一种“日志提供方兼容合同”的闭集：Password4j 没有提供方，Spotless 只承担编译与选定格式化路径合同，RabbitMQ 才检查 Logback 提供方。若“旗舰项目包”要求统一的运行时合同或目标仓原生失败测试，本包仍不满足；若项目包允许按真实消费方式定义不同仓库合同，则可以接纳，但必须保留这种异质性说明。

## 三臂证据核对

九个执行单元加入的 `LoggingProviderCompatibilityTest` 完全一致。它实际调用 `LoggerFactory.getLogger(...)` 与 `LoggerFactory.getILoggerFactory()`，并要求后者为 Logback 的 `LoggerContext`。这不是目标仓原生测试，而是数据集新增的观察合同；其合理性来自目标仓已经显式配置测试范围 Logback，而不是来自原有 114 项测试的期望。

- A0：SLF4J 1.7.36、Logback Classic/Core 1.2.11，三轮均为 115 项通过。
- A1：只把 SLF4J API 改为 2.0.0，Logback 仍为 1.2.11。三份归档测试报告都显示 115 项中仅新增合同 1 项失败，失败值均为 `NOPLoggerFactory`，其余 114 项通过。
- A2：保持 SLF4J 2.0.0，只把 POM 中 `logback.version` 从 1.2.11 改为 1.4.0。解析结果中 Logback Classic 与其传递的 Core 同步变为 1.4.0，三轮均恢复为 115 项通过。

A1 到 A2 的目标仓内容差异是一行 Logback 版本属性；不能把它表述成“解析依赖图只有一个构件变化”，因为 Logback Core 会随 Classic 一起改变。这个传递变化正是同一提供方修复的一部分，不破坏归因。

PR 190 是 Dependabot 生成、维护者合并的真实目标仓变更，且紧随 SLF4J 升级之后。它可以称为“维护者合并的精确协调改动”，但现有材料没有维护者亲自诊断新增合同失败的记录，因此不应写成“维护者针对该失败设计的修复”。一周后的维护者提交明确恢复 SLF4J 1.7 与 Logback 1.2 的兼容组合，反而强化了“版本组合需要协调”的语义，同时限定了 A2 只是短期被合并的策略。

## A3 兼容控制

六个执行单元固定同一 RabbitMQ 提交、同一新增合同与 Logback 1.2.11。三轮前臂的版本补丁都只把 `slf4j-api.version` 改为 1.7.29，三轮后臂都只改为 1.7.30；解析依赖也与预期一致。两侧每轮均执行 115 项测试且全部通过，提供方合同各执行一次。

因此，A3 能支持的结论只是：普通 `LoggerFactory` 初始化和 Logback 1.2.11 提供方选择在 1.7.29 与 1.7.30 两侧保持兼容。1.7.30 的关键修改涉及初始化失败后的替代日志器修复、事件重放和清理；当前合同没有主动触发初始化失败、事件积压或并发清理。三轮稳定不能把这个普通成功路径提升为对这些变化分支的直接验证。A3 可保留为窄兼容控制，不应作为“已覆盖 1.7.30 新行为”的证据。

## 两个限定负例

Password4j 的原边界仍成立。三轮中 A0 与 A1 都执行 206 项原生测试并通过，日志也分别显示旧版缺少静态绑定、新版没有提供方。它证明的是：在**没有日志提供方**的固定依赖图中，已执行的功能路径不需要因 SLF4J 2 修改目标仓。它不证明任何日志输出或提供方组合兼容。

Spotless 的原边界也仍成立。正式命令编译所需源集，并三轮执行直接进入 `LoggerFactory` 生产路径的 FreshMark 与 SortPom 三项测试；SLF4J 在相关源集中是仅编译依赖。它证明的是编译合同和这三项格式化路径不需要目标修改，不证明完整测试集稳定，也不证明任意运行时日志提供方兼容。

这两个负例没有被 RabbitMQ 的新合同推翻，因为三者观察的合同不同。反过来，也不能用这两个负例为 RabbitMQ 的提供方标签提供“同合同阴性对照”。四仓集合展示的是不同消费模式下是否需要协调，而不是统一提供方合同的四次重复。

## 最终裁决

- 接受 RabbitMQ 为一个有边界的正关系，证据强度为“新增可观察合同加精确三臂执行，并有维护者合并的相邻依赖协调改动”。
- 不把新增合同说成目标仓原生回归测试，不把 PR 190 说成维护者明确诊断后的人工修复。
- 保留 A3，但只作为普通初始化路径的兼容控制。
- 保留 Password4j 与 Spotless 的原限定负标签；二者都不是日志提供方兼容负例。
- 四仓包可以按“异质消费合同下的闭合集合”进入后续验收；若正式口径要求统一运行时合同或原生失败测试，则应继续标为不完整，而不是用三轮稳定性降低准入标准。

本次仅复核已有补丁、依赖树、测试报告与历史材料，没有重新执行实验，也没有修改正式标签或公共台账。
