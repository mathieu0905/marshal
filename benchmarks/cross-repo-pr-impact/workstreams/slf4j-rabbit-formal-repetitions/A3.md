# RabbitMQ 的 SLF4J 兼容控制重复

本补充实验只验证一个兼容控制，不改动既有 A0、A1、A2 的九次正式结果。

固定消费仓为 `rabbitmq/rabbitmq-jms-client` 的提交 `41b2abf72827e123c8c472d3f07b30ac3bc24be0`。A3 前臂只把 `slf4j-api.version` 改为 1.7.29，后臂只改为 1.7.30；两臂均保留 Logback Classic 和 Core 1.2.11，并加入同一个 `LoggingProviderCompatibilityTest`。

每轮、每臂都从固定提交新建检出，并使用该次执行独享的 Maven 本地仓库。运行器先在项目内用空仓执行一次 `dependency:go-offline`，形成这个项目所需的小型依赖种子，再为六个执行单元分别复制；不会复制用户的全局 Maven 仓库。镜像、检出、缓存和 Java 临时文件均位于项目的 `.work/slf4j-rabbit/`。执行前保存输入差异和解析后的依赖树，随后运行完整的 `mvn clean test`。三轮的两臂都必须满足：

- 实际解析的 SLF4J API 分别为 1.7.29 和 1.7.30；
- 实际解析的 Logback Classic 与 Core 均为 1.2.11；
- 115 项测试全部通过，没有失败、错误或跳过；
- 新增合同实际执行，并确认 `LoggerFactory.getILoggerFactory()` 返回 `LoggerContext`。

SLF4J 1.7.30 调整了初始化后的替代日志器修复、事件重放与替代工厂清理。这里的合同验证普通日志提供方初始化在相邻版本两侧保持成立，不声称覆盖初始化失败或并发清理的全部变化路径。三次重复只衡量固定输入下的执行稳定性，不是三个独立关系，也不替代独立语义复核。
