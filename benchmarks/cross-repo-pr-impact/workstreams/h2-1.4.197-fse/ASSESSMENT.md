# H2 1.4.197 的 FSE 关系族筛选

更新日期：2026-08-25

## 结论

FSE 2024 中与 H2 1.4.197 精确关联的候选共有 5 条，包含 6 个失败观察。按真实 Git 根仓和共享变化面折叠后，只有 4 个独立关系：`davidmoten/state-machine`、`davidmoten/rxjava-jdbc`、`yegor256/jpeek` 与 `ontop/ontop`。其中 `state-machine` 的两条记录只是同一根仓中两个模块执行了同一生成键合同，不能拆成两个案例。

四个根仓的完整可达历史都没有在 POM 中采用过 1.4.197，因此都不存在“固定 H2 1.4.197、由目标仓维护者完成恢复”的历史 A2。本轮正式接纳 0 条，不执行三臂。`state-machine` 与 `rxjava-jdbc` 各自保留一个精确上游机制和一个后续维护者适配，作为高质量机制锚点；它们不能冒充固定 1.4.197 的因果正例。

## 候选框与去重

| 候选 | 根仓 | 模块或观察 | 裁决 |
|---|---|---|---|
| `0097`、`0098` | `davidmoten/state-machine` | shopping 与 persistence 均在生成键读取处报 `[2000-197]` | 合并为一个根仓关系，无合格 A2 |
| `0099` | `davidmoten/rxjava-jdbc` | 多行插入的生成键从 `[2]` 变为 `[1, 2]` | 无合格 A2 |
| `0103` | `yegor256/jpeek` | Windows 临时 JAR 被占用，目录清理失败 | 环境噪声，且无合格 A2 |
| `0111` | `ontop/ontop` | 数据库只读异常与端口占用两个观察 | 一个机制未隔离、一个环境噪声，且无合格 A2 |

5 条工作簿记录不是 5 个独立关系。`state-machine` 的两条记录共享根仓、依赖图、生产实现和后续修复；`ontop` 的两段异常属于同一条候选记录，其中端口占用也不能作为 H2 行为标签。

## 上游变化边界

H2 标签 `version-1.4.196` 解引用为 `1c6e22a...`，`version-1.4.197` 解引用为其后代 `c8a861bb...`。两者之间有 1443 个提交，是有效的向前版本边界，但变化面很大，不能把整个版本差当成一个机制。

`state-machine` 的精确机制是 `58a30eba...`：H2 从此只在调用者明确请求时返回生成键。该提交不在 1.4.196 中，而在 1.4.197 中。目标代码使用普通的 `prepareStatement(sql)`，随后直接读取生成键，因此两个模块都在 `SimpleResultSet.getLong` 报“没有可用数据”。

`rxjava-jdbc` 的精确机制是 `e05502f1...`：H2 开始返回多行插入产生的多个键。该提交同样只在 1.4.197 一侧。工作簿保存的断言恰好从旧行为的 `[2]` 变成新行为的 `[1, 2]`。

## 目标历史审计

### State-machine

完整远程引用共有 1070 个可达提交。所有 POM 历史中，1.4.197 的采用次数为 0。

维护者提交 `32f8791c...` 很有价值：提交说明明确称新版 H2 更严格，并把三处 `prepareStatement(sql)` 改为显式请求 `Statement.RETURN_GENERATED_KEYS`。但是同一个提交把 H2 从 1.4.191 升到了 1.4.200。把这三处代码移植回固定 1.4.197，可能形成漂亮的消融实验，却不能把原历史提交改写成固定 1.4.197 的 A2。

### RxJava JDBC

完整远程引用共有 1259 个可达提交，POM 历史中同样没有 1.4.197。

维护者提交 `398cdefe...` 把断言从 `[2]` 改成 `[1, 2]`，与工作簿失败完全对应；但它同时将 H2 从 1.4.192 升到 2.1.210。恢复来自另一份源输入，不能作为固定 1.4.197 的历史 A2。

### JPeek

完整远程引用共有 1379 个可达提交。H2 从 1.4.193 直接跳到 2.1.210，从未采用 1.4.197。

公开异常只有 Windows 文件句柄与 JUnit 临时目录清理栈，没有 H2 栈或版本特异行为。仓库后来确有临时目录治理提交，但这不足以把操作系统资源占用归因于 H2 1.4.197。

### Ontop

完整远程引用共有 17727 个可达提交。项目长期固定 H2 1.4.196，后来直接尝试 2.x；POM 历史中没有 1.4.197。

只读异常确实执行到 H2 打开数据库并重放约束元数据的路径，是可继续研究的机制线索，但当前没有定位到版本边界内的精确源提交，也没有目标仓维护者 A2。另一条“19123 端口已占用”明确是运行环境冲突，不能贡献源影响标签。

## 为什么不执行三臂

普通测试可以验证两种人工方案：给 `state-machine` 移植显式生成键参数，或把 `rxjava-jdbc` 的期望改成两个键。这只会证明方案在 1.4.197 下可行，不会证明目标维护者当时作出了该修复。

这里的具体误标风险，是把 2021 或 2022 年在 H2 1.4.200、2.1.210 下完成的适配倒贴到 2018 年的 1.4.197 上。Git 能固定历史提交，版本号能固定依赖，测试能验证移植后的结果，但三者都不能把一个后续源版本下的维护行为变成固定 1.4.197 的历史 A2。因此准入检查在真实代码执行前已经给出决定性否定，不再用构造实验挤占采集时间。

## 证据边界

本组证明了两个独立消费仓分别命中 H2 1.4.197 的两个精确生成键机制，也证明两个后续维护者改动与公开失败高度对应。它不证明任何目标仓在固定 1.4.197 下完成维护者恢复，不提供正式三臂、限定负例或 A3。
