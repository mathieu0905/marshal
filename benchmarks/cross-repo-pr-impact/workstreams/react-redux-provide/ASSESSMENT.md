# React Redux 到 React Redux Provide 因果筛选

更新日期：2026-08-24

## 结论

本轮接受一个链独立的单正例三臂候选：`react-redux` 从 4.1.2 升到 4.2.0 后，`react-redux-provide` 5.1.0 的原生测试在加载生产模块时稳定失败；只加入维护者随后发布的生产导入替换及其新依赖后，同一命令恢复。这个关系的答案仓是实际需要修改的中间依赖仓 `loggur/react-redux-provide`，不是公开复现包列出的顶层传播仓 `react-redux-provide-theme`。

同一目标上另有一个独立兼容变化增强臂成立：`react-redux` 4.0.5 到 4.0.6 确实改变三个工具模块的导出合同，目标的六项原生测试在两侧都通过。当前没有限定负例标签；三臂只执行一次，尚未做隔离重复和独立语义复核。

本轮计数为：链独立 A0/A1/A2 正例一条、限定负例零条、A3 一条。

## 公开线索与标签校正

线索来自 Zenodo 记录 `10.5281/zenodo.5558085`。原记录以 `react-redux-provide-theme` 为顶层客户端，给出的真实依赖链是：

`react-redux-provide-theme → react-redux-provide → react-redux`

记录同时明确把 `fixed_client` 写为 `react-redux-provide`，并把恢复版本写为 5.2.0。因此，这里把顶层仓只当作失败传播线索，仓库级答案落在真正改变生产代码的中间仓。不能把一条中间修复重复标成顶层仓和中间仓两个独立目标。

公开复现包对顶层主题包的历史测试均记为错误，不能为本轮提供 A0。这里的三臂完全来自实际修复仓自身的原生测试重放，不继承论文执行结果。

## 源变化

`react-redux` 4.1.2 的发布提交为 `0ec547ec39a8139993124161e5c20142a289c2c0`。4.2.0 的发布提交为 `4f1d1c3c185ac83c1f52c0ae4c613a8fe9d75ac2`，其中生产变化提交 `c4ef6f9417438b887be683d4720ffa6fb4b207f9` 将 `connect` 改为使用 `lodash/isPlainObject`，并删除公开发布物中的内部路径：

`react-redux/lib/utils/isPlainObject`

目标 5.1.0 直接导入这个内部路径。因而 A1 的失败表面不是根据错误消息猜测出来的间接关联，而是源提交删除的文件与目标生产导入逐字对应。

## 维护者真实修复

npm 发布元数据把 `react-redux-provide` 5.1.0 指向 Git 提交 `72bba55b6464ae2dfa060ecb04a3346e35d8bf04`，把 5.2.0 指向 `0874512bd12ad1491465463f4566ae60f5e8fcf6`。原 GitHub 仓已经删除；Software Heritage 保存了完整历史，并显示二者之间只有维护者提交 `977596ce1864d01beabc02fdbf6f347ad3f94255`，随后是 5.2.0 版本提交。

5.1.0 与 5.2.0 的 `src/provide.js` Git 内容标识分别是 `6a117ab...` 与 `df926a2...`。维护者生产修复只把：

`react-redux/lib/utils/isPlainObject`

替换为：

`is-plain-object`

并在生产依赖中加入 `is-plain-object ^2.0.1`。同一发布还更新了文档、测试夹具提供方和构建产物；A2 没有带入这些无关变化，只应用 `maintenance-production-repair.patch` 中的一行生产导入替换，并安装维护者声明的 2.0.1 依赖。

## 三臂执行

每个臂从 npm 的 `react-redux-provide 5.1.0` 发布物建立新目录，执行原生命令：

`npm test -- --reporter dot`

该命令通过 Babel 加载目标 `src/provide.js`，并运行仓库随发布物提供的完整六项测试。发布物把自身列作开发依赖；工作流在每个臂都删除这一项，避免现代 npm 额外安装另一个目标版本。这个相同的环境处理不改变生产代码，且不会造成三臂差异。

| 臂 | React Redux | 目标生产修改 | 结果 |
|---|---:|---|---|
| A0 | 4.1.2 | 无 | 6 项通过 |
| A1 | 4.2.0 | 无 | 进程退出 1；加载 `src/provide.js` 时精确报告旧 `isPlainObject` 路径不存在 |
| A2 | 4.2.0 | 只加入维护者生产导入替换及 `is-plain-object 2.0.1` | 6 项通过 |

A1 在收集测试时失败，因此没有单项测试计数。这不是“测试没有覆盖”的普通安装失败：原生命令已经进入目标生产入口，并在源变化删除的精确导入表面中止。A2 保持相同源版本、目标基准和命令，只替换这个导入后恢复。

执行环境为 Node.js 20.20.2，而公开工件记录的顶层仓实验使用 Node.js 5.11.1。由于 A0 在同一现代环境通过，A1 又只出现与源删除逐字一致的单一模块加载错误，当前证据足以排除一般性运行时漂移；但不能声称已经恢复完整的 2016 年传递依赖环境。

机器结果位于 `results/react-redux-provide-screening-2026-08-24/summary.json`，每臂还保留安装日志、原生测试日志、退出状态和实际版本。

## A3 兼容变化增强臂

独立源变化选用 `react-redux` 4.0.5 到 4.0.6。维护者提交 `caae2e1d53775b89716683f7d6a5d8302cad5a87` 为修复旧浏览器构建，把 `isPlainObject`、`shallowEqual`、`wrapActionCreators` 等内部工具从 Babel 默认导出改回 CommonJS 导出。目标 5.1.0 会直接导入这些工具，因此这不是未进入候选代码的普通绿色版本对。

补充探针确认变化实际可见：

- 4.0.5 的 `isPlainObject` 原始导出是带 `default` 键的对象；
- 4.0.6 的原始导出直接是函数；
- 目标的 Babel 导入在两侧都规范化为函数，并对普通对象返回真、对数组返回假；
- 同一组六项原生测试在两侧均通过。

这个 A3 只支持“目标在该工具导出合同变化下无需修改”。它不说明所有 React Redux 行为均兼容，也不替代破坏三臂。

## 限定负空间

本轮没有构造限定负例。源变化的判定表面是一个被删除的内部模块路径：仍直接导入该路径的仓库按定义会在加载时失败，而只使用 React Redux 公共接口的普通绿色仓没有进入这个删除表面。没有发现带有自身兼容分支、又由原生检查执行该分支的独立消费仓，因此不能用一般 React Redux 消费者补成负标签。

## 证据边界与后续条件

这条关系已满足同命令 A0/A1/A2、确定性精确失败和维护者真实生产修复恢复，可作为一条单正例三臂候选。它尚不支持完整项目包或正式排行榜标签，仍需：

1. 三次隔离重复，确认安装和测试结果稳定；
2. 独立语义复核，确认 A2 的一行生产抽取和新依赖构成完整最小恢复；
3. 如需报告克制能力，另建候选目录并寻找真正执行删除表面兼容分支的仓库，不能用普通公共接口消费者代替。
