# request 2.18.0 与 PolyClay 候选关系筛选

更新日期：2026-08-24

## 结论

这条候选关系正式拒绝，不进入跨仓因果数据集。公开数据把 `request 2.18.0` 记为破坏 PolyClay、并由 `polyclay 1.4.0` 修复；真实调用链重放得到相反方向：旧版 `request 2.16.6` 会在 Cradle 包装空响应时崩溃，`request 2.18.0` 将空响应体规范化为空字符串后，回调能够正常结束。

`polyclay 1.4.0` 也不是针对这个行为的兼容修复。维护者删除了 Couch、Redis、Levelup 和 Cassandra 四个适配器及其测试，把适配器迁往独立仓库。升级后同一 Couch 合同根本无法执行，因此不能把删除功能当作 A2 恢复。

本工作流正式接纳零条，限定负例零条，A3 零条。

## 候选来源

候选来自 Zenodo 记录 `10.5281/zenodo.5558085`。其中 PolyClay 记录声明：

- 消费仓：`ceejbot/polyclay`；
- 间接依赖链：PolyClay → Cradle → request；
- 提供方变化：`request 2.18.0`；
- 消费方恢复版本：`polyclay 1.4.0`；
- 恢复方式：消费方代码修改并删除 Cradle。

论文随附说明进一步称，`request 2.18.0` 在请求体引入空字段，消费方通过删除测试和 Cradle 依赖修复错误。这些记录只作为待核线索，没有直接继承为真值。

相关公开证据：

- request 变化提交：`d05b6ba72702c2411b4627d4d89190a5f2aba562`；
- PolyClay 修复候选：拉取请求 12，头提交 `8d4960278b9bf1b92fcc908ce9c07aeb8c992c0f`；
- PolyClay 1.3.0 标签提交：`87f22793915824cbd77662a84a88a2d4c8d4d7aa`；
- PolyClay 1.4.0 标签提交：`3fb792751e1e59d0782c01797a538aa11cbf08b6`；
- Cradle 固定版本：`0.6.5`，其 `request` 依赖范围是 `2.x.x`。

## 真实变化表面

request 提交 `d05b6ba...` 的关键修改是：当响应体未定义且不是 JSON 请求时，把 `response.body` 设为空字符串。Cradle 0.6.5 随后会把 request 回调的响应体交给自己的 `Response` 包装器。

在旧版 request 中，空 HTTP 响应的回调体是 `undefined`。Cradle 构造响应时读取 `json._id`，因此抛出类型错误，消费方回调不会执行。request 2.18.0 把同一响应体变成空字符串，Cradle 能完成包装并调用 PolyClay 回调。这里验证的是变化代码进入原生依赖链后的实际行为，而不是仅比较依赖版本或普通绿色构建。

## 三臂重放

`run_screening.sh` 为每一臂安装固定的 npm 版本，并启动本地 HTTP 服务返回真实空响应。探针执行：

`PolyClay CouchAdapter.remove → Cradle Database.remove → request 回调`

| 臂 | 固定输入 | 实际结果 |
|---|---|---|
| A0 | PolyClay 1.3.0、Cradle 0.6.5、request 2.16.6 | 适配器存在；Cradle 读取 `undefined._id` 时抛错；消费方回调未执行 |
| A1 | PolyClay 1.3.0、Cradle 0.6.5、request 2.18.0 | 适配器存在；消费方回调执行；响应 JSON 为 `""` |
| A2 | PolyClay 1.4.0、Cradle 0.6.5、request 2.18.0 | `CouchAdapter` 已被删除，同一合同无法执行 |

结果与“旧版通过、升级后失败、消费方修复后恢复”的正例结构完全不符。这里不是不确定复现，而是执行证据直接推翻候选标签。

原始结果位于 `results/request-polyclay-screening-2026-08-24/`。

## 恢复提交的性质

头提交 `8d496027...` 的提交说明明确表示适配器已迁往各自独立仓库，因此从主仓删除。该提交共修改 13 个文件，增加 23 行、删除 3442 行，主要内容是：

- 删除四个数据库适配器；
- 删除四套适配器测试；
- 删除相应可选依赖；
- 修改文档，链接新的独立适配器仓库。

这类功能迁移可以成为别的跨仓研究对象，但不能作为 request 空响应行为的兼容修复。它没有在相同合同上证明 A2 恢复。

## 负空间与 A3 搜索

Zenodo 的 64 条记录里，`request 2.18.0` 只对应这一条 PolyClay 记录。补充搜索检查了空响应断言和 request 消费仓，命中主要是 request 自身测试的复制、现代无关代码或随仓依赖副本。没有找到同时满足以下条件的历史消费仓：

- 确实通过原生合同执行 request 2.18.0 的空响应变化；
- 能证明在限定候选目录中未受影响；
- 或具有独立真实兼容变化，可形成 A3。

因此本轮不从弱搜索命中制造限定负例，也不把普通绿色结果标成 A3。

## 准入判断

该候选同时违反两个正例要求：A0/A1 的因果方向相反，所谓 A2 又删除了被测合同。后续除非出现新的历史证据证明另一条独立消费链确实被 `request 2.18.0` 破坏，否则不再把 PolyClay 1.4.0 作为恢复点重试。
