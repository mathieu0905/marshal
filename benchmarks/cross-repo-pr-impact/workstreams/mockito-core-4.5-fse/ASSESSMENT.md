# Mockito Core 4.5.0 的 FSE 关系族筛选

更新日期：2026-08-25

## 结论

完整精确版本框共有 2 条候选、3 个失败观察，去重后对应 `alibaba/nacos` 和 `robvanderleek/JLifx` 两个独立根仓。本轮正式接纳 0 条，没有执行 A0、A1、A2，也没有限定负例或 A3。

必须准确区分本组版本：目标项目声明的是 Mockito 3.8.0，FSE 的最后通过探针是 4.4.0，首个失败探针是 4.5.0。本组不是现有工作流中的 3.12.4→4.0.0，也不是 3.12.4→4.1.0。

两个目标的完整历史都没有采用 4.5.0，也没有保持 4.5.0 的维护者 A2。Nacos 后来从 3.8.0 直接迁到 4.11.0，同时改造 JUnit、测试插件和依赖管理；JLifx 只有一个未合并的 4.5.1 自动升级提交。工作簿又没有保存目标 Git 修订，因此不能把后来的不同版本迁移改写为本题 A2。

两个目录提示、远程仓库和历史身份均不相同，所以这里确实是两个根仓。

## 源变化边界

Mockito 4.4.0 标签提交为 `813add00ecd9a78ea9dcfccfc7797ea242be9ca9`，4.5.0 标签提交为 `2c0bf94609300ed369198c3bd44c1555e88f8998`。两者之间不只有一个生产变化：

- `aabb8f62a2b44e99938d0cccf17e9877f4fc6189` 删除内部集合与字段工具，并重写字段筛选；
- `d539af2d7afdcfaf1eda4a57911d7f9df107db2a` 调整内联模拟对 Groovy 方法的处理；
- `d23dc0e57a8360c8d80f69096cee24c20e4c7c26` 改造子类模拟生成以支持 GraalVM。

Nacos 的公开日志只显示测试初始化后 `rpcClient` 未能留下可用值，随后在清理阶段发生空指针异常。它没有保存更早的初始化异常，也不足以在上述变化中锁定一个源提交。

JLifx 的情况更弱：失败的 `BulbDiscoveryServiceTest.testDiscoverGatewayBulb` 不导入、不调用、不配置也不验证 Mockito。它启动本地 UDP 模拟设备，再断言只发现一个设备；实际发现两个设备更像网络发现或共享静态状态的观察。仅凭“改了 Mockito 版本后断言不同”不能把它归因到 Mockito 生产代码。

因此，本组只能保留 4.4.0→4.5.0 的发布边界，不能声称找到一个共同的精确源机制。

## Nacos 历史审计

公开堆栈把异常定位到 `RpcClientTest.tearDown` 第 137 行，即 `rpcClient.labels.clear()`。该测试最早出现在提交 `3109d57c266d5505d62cc9d880cdcc078b93d776`，合入默认分支的提交为 `4a134b233c416b242b5011f32edb3c21f976f004`；直到 `5e55d4b1b66f556e405e7bd4e9aa5a58317c6a14`，第 137 行仍是相同语句。工作簿没有从这个窗口中选择唯一修订。

远程镜像共有 5580 个引用和 23408 个唯一可达提交。全历史没有 Mockito 4.5.0。2024 年合入的拉取请求 12024 通过提交 `b2e506d7fef3a7310a806d3b5cb907bdbda34ca6` 把 3.8.0 改到 4.11.0，同时引入 Mockito BOM、JUnit 5、Vintage 引擎、Mockito Jupiter，并升级 Surefire 和 Failsafe。它既改变源输入，也不是针对这两个公开失败方法的独立修复，不能充当 4.5.0 的 A2。

## JLifx 历史审计

远程镜像共有 289 个引用和 625 个唯一可达提交。全历史没有 Mockito 4.5.0。最接近的拉取请求 194 只把 POM 中的 Mockito 3.8.0 改成 4.5.1，提交为 `da63f1adfd1b95f8ce6ea89d19731b95d83eb6d8`；该请求已关闭且未合并，没有目标代码或测试修复。

项目后来在默认分支使用更高 Mockito 版本，但失败测试从 2020 年起没有相应维护者修复。普通绿色构建也不能证明本地 UDP 发现断言触及 Mockito 4.5.0 的变化代码，所以后续版本不能倒推成 A2 或负例。

## 为什么不执行三臂

Nacos 没有唯一目标修订、没有单一源机制，也没有固定 4.5.0 的维护者恢复。若选择窗口内任意提交，再从 2024 年的大规模 JUnit 迁移中抽取作者认为有用的部分，会同时制造 A1 输入和 A2 边界。

JLifx 的失败测试没有 Mockito 调用路径。重复运行 3.8.0 与 4.5.0 即使再次得到 1 个和 2 个设备，也无法排除 UDP 环境或静态状态漂移；普通测试重复不足以建立源因果关系。为这种非归因断言编写清理代码同样会是数据集作者修复。

按当前准入顺序，两仓都应在执行前停止。它们可以作为 FSE 合成升级记录的质量审计样本，但不能进入旗舰因果正例。

## 证据边界

本组证明 FSE 在两个独立仓库中记录了 4.5.0 升级后的失败现象。它不提供精确源提交、精确目标修订、维护者 A2、限定负例或 A3。特别是 JLifx 记录不应仅因依赖版本是唯一实验变量就被表述成 Mockito 行为变化。
