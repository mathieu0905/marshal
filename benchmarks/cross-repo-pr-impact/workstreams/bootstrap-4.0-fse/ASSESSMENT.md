# Bootstrap WebJar 3.4.1 到 4.0.0 的 FSE 关系族筛选

更新日期：2026-08-25

## 结论

FSE 2024 的完整精确版本框共有 3 条候选、3 个失败观察。两个 Ninja 目录实际是同一个仓库：旧地址 `reyez/ninja` 会重定向到 `ninjaframework/ninja`，两者的 Git 端点也返回同一个提交。去重后只剩 Ninja 与 Wicket Bootstrap 两个根仓。

本轮正式接纳 0 条，未执行 A0/A1/A2，也没有限定负例或 A3。核心原因不只是“没有修复”，而是源输入本身不构成一条真实的向前变化：Bootstrap WebJar 4.0.0 发布于 2018-01-18，作为旧臂的 3.4.1 反而发布于 2019-02-19。它们是两个并行大版本发布线上的制品，不存在从 3.4.1 前进到 4.0.0 的上游提交或拉取请求。

两个目标的完整历史也都没有采用固定的 4.0.0，更没有维护者精确 A2。继续执行只会选择一个未记录的目标提交，再由数据集作者制造修复，不能产生正式因果标签。

## 源输入边界

`webjars/bootstrap` 的发布历史给出三个关键事实：

- `278628ce...` 在 2018-01-18 发布 4.0.0，其 POM 依赖 jQuery 3.0.0 和 Popper 1.11.1；
- `8fd178cb...` 在 2019-02-19 发布 3.4.1，其 POM 依赖 jQuery 1.11.1；
- `50142a99...` 是 Bootstrap 4 打包线引入 jQuery 3.0.0 与 Popper 的精确提交，但它发生在 2017 年，早于两个正式发布。

因此 Ninja 的异常有可信机制线索：跨大版本替换会把旧 TinyMCE 所处的 jQuery 依赖线从 1.11.1 改成 3.0.0。可是这个比较不是从旧提交到新提交的单向变化，不能作为 Marshal 的真实上游变更输入。

Wicket 的断言更弱：它直接证明解析出的制品版本是 4.0.0，但没有命中 Bootstrap 行为变化。把这种版本身份断言当作跨仓影响，会把“测试写死旧路径”与“上游实现破坏”混为一谈。

## Ninja 历史审计

完整远程引用共有 2859 个可达提交。`reyez/ninja` 返回 HTTP 301 到 `ninjaframework/ninja`，不是第二个独立仓库。

Ninja 的根 POM 在 2015 年由 `54b0add4...` 固定到 Bootstrap WebJar 3.3.4，当前开发分支仍保持 3.3.4。历史中没有 4.0.0 的维护者采用，也没有在 4.0.0 下修复 TinyMCE 浏览器合同的提交。工作簿还没有记录当时执行的目标 Git 修订。

## Wicket Bootstrap 历史审计

完整远程引用共有 4369 个可达提交。Wicket 8.x 主线后来采用 3.4.1，但维护者的 Bootstrap 4 分支并未采用 4.0.0：

- `e0b942e0...` 从 3.3.7-1 直接迁到 4.1.0，同时把 Less 改成 Sass、增加 Popper、修改资源引用并改动 84 个路径；
- `5e9e3307...` 确实只修改一行测试期望，但对应的是 4.1.0 到 4.1.2，而不是本候选固定的 4.0.0。

前者是宽泛大迁移，后者是不同源输入下的精确修复。两者都不能被移植成 3.4.1 到 4.0.0 的 A2。工作簿同样没有记录具体目标提交。

## 为什么不执行三臂

普通测试可以验证作者选择的某个 Wicket 提交在替换依赖后是否红，也可以验证把字符串改成 4.0.0 后是否绿；Git 和版本号则能固定这个人工实验。但它们都不能补出两个缺失事实：真实向前的源提交，以及维护者在固定 4.0.0 下作出的恢复。

具体误标场景是把 2019 年的 3.4.1 倒换成 2018 年的 4.0.0，再把 Wicket 维护者面向 4.1.x 的独立迁移或一行测试修复移植回来，宣称这是 4.0.0 的维护者适配。按正式准入顺序，本组应在执行前停止。

## 证据边界

这组三条记录继续保留为跨大版本替换风险线索：Bootstrap 4 WebJar 的传递依赖变化会影响旧前端库，硬编码资源版本也会立即暴露替换。它们不提供真实向前源提交、精确目标修订、固定 4.0.0 的维护者 A2、限定负例或 A3，因此不能进入旗舰正式包。
