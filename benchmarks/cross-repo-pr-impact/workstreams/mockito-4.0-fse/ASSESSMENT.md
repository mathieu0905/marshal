# Mockito 4.0.0 FSE 关系族评估

## 结论

本关系族完整保留 6 条候选记录，经仓库编号与重定向去重后对应 4 个独立客户端根历史。只有 Hazelcast 留下 Mockito `4.0.0` 的实际升级分支，但该分支只有版本修改，没有后继维护者恢复。其余三仓都没有在固定 `4.0.0` 下产生恢复提交。

因此精确 A2 为 0，不执行客户端 A0/A1/A2 重放，本关系族产出 0 个可接纳因果案例。

## 候选框与根仓

- `0577` 对应 `google/error-prone`。
- `0579` 对应 `hazelcast/hazelcast-kubernetes`。
- `0580` 与 `0581` 是 `googleads/googleads-java-lib` 的两个模块，属于同一根历史。
- `0583` 与 `0584` 是历史仓 `farao-community/farao-core` 的两个模块。该地址当前重定向到 `powsybl/powsybl-open-rao`，仓库编号保持为 `158683766`，属于同一根历史。

## 源机制

Mockito 标签 `v3.12.4` 是 `v4.0.0` 的祖先。提交 `caf35b24...` 属于 `v4.0.0`、不属于 `v3.12.4`，一次性删除了已弃用接口。该提交改动 203 个文件、增加 918 行、删除 2732 行，是宽清理提交。

其中删除 `org.mockito.runners.MockitoJUnitRunner` 可以精确解释 `0577`：FSE 记录的测试源码仍导入旧包，因此在 `4.0.0` 下直接编译失败；新的 `org.mockito.junit.MockitoJUnitRunner` 仍然存在。核心删除差异见 `source-mechanism.patch`。

`0579`、`0580`、`0581`、`0583`、`0584` 均涉及 PowerMock、参数匹配或模拟生命周期与 Mockito 的交互。现有 FSE 日志没有保存足以定位到某个 Mockito 源提交的调用链，不能仅凭同一版本号把它们归到旧运行器删除机制，也不能从 203 文件的发布差异中主观挑选一个机制。

## 固定版本 A2 审计

### Error Prone

`1be20906...` 在 Mockito `4.0.0` 发布前，把依赖从 `2.25.0` 升到 `3.12.4`，同时将旧运行器导入改为新包名。这是有价值的维护者迁移证据，但源输入仍是 `3.12.4`。仓库后来直接从 `3.12.4` 升到 `4.6.1`，没有固定 `4.0.0` 的恢复。

### Hazelcast Kubernetes

PR 346 的头提交 `5a149b97...` 只把 Mockito 从 `3.12.4` 改到 `4.0.0`。该提交未合并且没有后继提交，候选失败涉及的 PowerMock 测试也没有在该分支修复。这提供了精确升级臂，但没有 A2。

### Google Ads Java Library

两个候选模块长期固定 Mockito `3.2.0`，直到旧 AdWords 模块被删除。全部可达历史中没有采用 Mockito `4.0.0`，删除模块不是恢复。

### Farao / Open RAO

`25df9f02...` 将两条候选涉及的测试从 JUnit 4 与 PowerMock 迁到 JUnit 5 和 Mockito 静态模拟，语义上确实消除了旧兼容层。但该提交仍把 `mockito.inline.version` 固定为 `3.5.10`，并且整个迁移改动 292 个文件。它不是固定 `4.0.0` 的 A2。

## 三臂可行性

四个根仓都缺少“保持 Mockito `4.0.0` 且由维护者完成恢复”的历史臂。把 Error Prone 的 `3.12.4` 预迁移、Farao 的 `3.5.10` 静态模拟迁移，或更高 Mockito 版本的升级当作 A2，都会同时改变源输入，无法把恢复归因于客户端修复。

FSE 材料也没有给出精确客户端修订。即使以后恢复出 A0/A1 时点，公开历史中不存在的固定版本 A2 仍无法补齐，因此本轮在重放前拒绝。

本工作流没有修改公共候选台账、结果索引或 `.claude`，也没有独立提交。
