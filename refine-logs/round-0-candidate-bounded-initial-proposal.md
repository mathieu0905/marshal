# 已知候选仓跨仓影响评测：初始设计

## Problem Anchor

- **Bottom-line problem**：给定一个源仓变更、项目内已知候选仓集合及其观察时点代码，判断并排序哪些候选仓需要检查、适配或联合验证。
- **Must-solve bottleneck**：现有建设路线把“发现全网相关仓库”“恢复因果正例”“构造可靠负例”和“找到兼容变化”同时设为每个项目包的准入条件，导致样本产率低、构造成本高，并偏离 Marshal 原始的已知关系路由设定。
- **Non-goals**：不从整个 GitHub 自动发现候选仓；不要求每条案例证明完整影响集合；不把未观察到修复的仓库标成负例；不要求每条案例具备 A3；不新增产品 gate、冻结 contract 或内容 hash。
- **Constraints**：复用现有 100 条输入、12 个候选目录和 1078 个时点仓库组合；正式推理离线；候选目录不得按单条答案构造；真实构建、测试和重放不能被静态前置检查替代。
- **Success condition**：形成一个可直接实现和验证的数据设计，使统一输出接口能够测量已知候选仓中的目标排序，同时严格按证据层分别解释历史适配与因果破坏，且不再因缺少完整四臂闭集淘汰已有高质量正例。

## Technical Gap

Marshal 最初面向 `node`，后来由 Cowboy Domain Pack 预登记 `wallet`、`runner`、`cbfs`、`cbss`、`cowboy` 与 `node` 的少量合同。它接收当前仓库和修改路径，选择已知合同及检查位置；它不从任意生态发现相关仓库，也不表达多仓候选版本组合。

当前数据路线把更难的开放世界关系发现和完整四臂因果闭集当成主任务。结果是，大量时间花在恢复陌生仓库历史、寻找维护者精确 A2、限定负例和 A3，而不是测量核心问题：在项目边界已经给定时，系统能否从候选仓中找出真正需要检查的仓库。

最小修正不是增加关系发现器，而是明确候选边界，并把证据强度与主任务准入拆开。

## Method Thesis

- **One-sentence thesis**：用标签无关、项目级固定候选目录限定搜索空间，复用一个目标仓排序接口，并把历史适配与因果破坏按证据层分开报告；A0/A1/A2、限定负例和 A3 是可叠加证据，不是每例必备结构。
- **Why this is the smallest adequate intervention**：现有输入、快照、评分器和 100 条案例已覆盖主任务，主要工作是修正文档、准入层级和报告口径，不需要先实现新的产品机制。
- **Why this route is timely**：现代代码代理擅长在给定多仓上下文中检索和推理，但开放世界仓库发现会混入托管平台覆盖和索引能力。固定候选边界能把评测集中到跨仓影响推理本身。

## Contribution Focus

- **Dominant contribution**：candidate-bounded cross-repository assessment，即给定真实时点候选仓代码、统一输出目标排序，并按证据等级限制结论的评测协议。
- **Supporting protocol**：把历史适配、可执行因果正例、有界负例和兼容变化控制分层记录；它不是第二项并列贡献。
- **Explicit non-contributions**：开放世界关系发现、永久依赖图、自动 companion PR 合并、所有候选仓联合构建、通用误报率估计。

## Proposed Method

### Complexity Budget

- **Frozen / reused**：现有 `inputs.jsonl`、候选仓目录、时点快照、隐藏目标标签、准备脚本和仓库排序评分器。
- **New**：候选目录准入规则、统一案例证据等级、执行子集协议和新的文档主线。
- **Intentionally excluded**：新的模型训练、全网检索器、每例四臂要求、额外 hash、全量候选仓构建。

### System Overview

```text
源 PR 差异
    +
固定项目候选目录 ----> 时点快照准备 ----> 受测系统
                                        |
                                        +--> 有序候选仓（统一主输出）
                                        +--> 影响位置/检查建议（次级诊断）
                                        +--> 执行状态（仅执行子集）

隐藏标签 ------------------------------------------------> 分层评分
```

### Candidate Boundary

候选目录必须按项目、生态或治理边界预先定义，并跨多条案例复用。不得根据某条案例的目标标签临时增删仓库。每个目录必须记录来源规则、生成时间、仓库纳入理由和使用案例数；只被一条案例使用的目录只能进入开发集或敏感性报告，不能进入正式主分数。每条案例至少有一个已核验目标和一个在截止时间可用的非目标候选；非目标候选默认是 `unjudged`，不是负例。

当前 `materialize_impact_discovery_set.py` 以“全部已知目标并入手工 `DISTRACTORS`”生成目录，因此现有 12 个目录尚未证明标签无关。`drizzle`、`opencontainers-image`、`wandertracks` 和 `zuul` 各只服务一条案例。现有 100 条可以继续用于开发和输入可运行性诊断，但正式评测前必须用独立项目名录重建或逐目录证明同一仓库集合本来就会被候选规则选中。

候选目录回答“系统应该检查哪些已知相邻仓库”，隐藏目标回答“公开证据已确认哪些仓库发生过实现、适配或修复”。二者不能混同。

### Evidence Ladder

| 层级 | 最小证据 | 可支持结论 | 不支持结论 |
|---|---|---|---|
| E1 已知适配 | 目标变更直接引用源变化，且人工确认语义 | 目标仓存在已核验历史采纳或适配 | 源变化必然导致失败、其他仓无影响 |
| E2 可执行正例 | A0 旧组合通过、A1 仅源变化失败、A2 精确目标适配恢复 | 目标仓对该输入存在因果破坏 | 未执行候选仓为负例 |
| E3 有界负例 | 候选仓任务实际消费变化表面，A0/A1 均通过 | 在该任务和输入范围内无观察影响 | 仓库整体永远不受影响 |
| E4 兼容变化 | 独立源变化进入相同消费表面，候选任务前后通过 | 系统对兼容变化的克制 | 每个 E2 案例都必须有 A3 |

E1 是历史适配排序层的准入下限。E2 是因果破坏层的准入下限。二者可以复用相同输入和输出接口，但必须分别计分和陈述结论，E1 成绩不能替代 E2 结论。E3、E4 可以独立附加；缺少 E3 或 E4 不会使 E2 降为无效正例。

现有标签到证据层的迁移规则为：

| 现有字段 | 新层级 | 迁移条件 |
|---|---|---|
| `specification_proven` | E1 | 保留现有人工语义确认 |
| `implementation_proven` | E1 | 保留现有目标提交语义确认 |
| `coordination_proven` | E0 候选线索 | 单独不能进入 E1 或 E2 |
| `ci_contrast_proven` | E2 候选 | 另核对 A0/A1/A2 组合、失败签名和目标修复后才能确认 |
| `executed` | E2 候选 | 另核对三个干预臂；普通双版本差异不能自动升级 |
| 工作流中的限定负例 | E3 | 需要单独 execution manifest；当前 case schema 不自动承载 |
| 工作流中的合格 A3 | E4 | 需要单独 execution manifest；不并入 E2 准入 |

### Output Semantics

主输出是有序候选仓列表。路径、测试、命令和执行结果只是次级诊断。v1 继续使用现有 `prediction-schema.json`：

- `fail`：实际执行观察到失败；
- `pass`：命令成功且确认执行到预期检查；
- `not_assessed`：未运行、缺少消费证明或证据不足；
- 因果组合结果仅在 E2 子集使用。

不能把“没有预测”解释为无影响，也不能把 repo-local pass 提升为跨仓 pass。

### Dataset Composition

1. **E1 历史适配排序层**：现有 100 条案例在候选目录来源审计和 split 前只作开发集；之后报告已知目标召回、MRR、Recall@K 和预测仓数量。
2. **E2 可执行因果层**：所有通过三臂复核的 OpenDev、主动重放和历史锚点；单独报告目标找回、检查位置和端到端执行判断，不能与 E1 混成一个因果分数。
3. **E3 有界负例层**：仅纳入满足 E3 的候选仓；只有同一 bounded universe 内正负候选都完整判定时才报告 precision/specificity，否则只报告 false-alarm、abstention 和预测数量。
4. **兼容变化子集**：已有合格 A3 独立组成，不再作为项目包成立条件。

### Split Design

当前 `index.jsonl` 的 100 条全部标为 `test`，尚未形成可用于产品结论的隔离 split。重划分必须先把共享同一有向关系的案例连成组，再把同一源提交族、兼容性机制和修复模板的组继续合并，最后在组级分配开发、正式和保留集。任何组不得跨 split。

分组键和顺序为：

- 同一源 PR 或源提交族；
- 同一有向源仓到目标仓关系；
- 同一兼容性机制和目标修复模板；
- 仓库别名、迁移仓和多模块记录先折叠到根仓。

分配目标以关系组数量为主，案例数和候选目录规模只作平衡项。单例候选目录全部进入开发或敏感性集。划分完成前，源仓到目标频率策略暴露出的强先验不能作为公平基线，所有 100 条结果都只能称为开发诊断。

主要统计单位是案例和有向仓库关系。重复命令、模块或测试不增加样本数。

## Failure Modes and Diagnostics

- **候选目录泄漏答案**：检查目录是否跨案例固定、是否包含至少一个可用干扰仓，并报告目录规模分布。
- **候选目录过宽**：同时报告 Recall@K、MRR 和平均预测数量；按目录规模分层。
- **标签不完整**：主集不报告 precision/F1；额外预测计作 unjudged。
- **源仓先验饱和**：源仓到目标频率只作标签泄漏诊断，不作为公平基线；按关系隔离评估。
- **训练记忆**：按年份与项目分层，并保留较新或非规范子集。
- **执行假绿**：保留零测试检测、版本核对和消费证明；未运行记为 `not_assessed`。

## Claim-Driven Validation Sketch

### Claim 1：已知候选边界足以形成非平凡跨仓排序任务

- **Minimal experiment**：先完成候选目录来源审计和关系隔离 split，再运行随机、名称/组织、标签频率诊断和至少一个读取候选代码的系统。
- **Metric**：MRR、Recall@1/3/5、平均预测仓数、按候选目录规模分层。
- **Decisive evidence**：读取候选代码的方法超过非语义策略，且提升不能由全报候选仓解释。

### Claim 2：证据分层能保留强因果案例而不伪造负空间

- **Minimal experiment**：把现有高质量案例按 E1-E4 重标，核对 E2 正例、E3 有界负例和 E4 兼容变化的独立数量与构造成本。
- **Metric**：各层独立案例数、根仓数、每例准备时间、从候选到接纳的产率。
- **Decisive evidence**：E2 数量显著高于“完整四臂项目包”数量，且所有负例仍满足消费与执行要求。

### Claim 3：排序与执行证据是互补能力

- **Minimal experiment**：在 E2 子集比较只做仓库排序、只做当前配置路由、排序后执行检查三种流程。
- **Metric**：目标找回、可运行检查率、真实失败/恢复判断正确率、`not_assessed` 比例。
- **Decisive evidence**：候选排序找得到目标，但只有真实组合执行能产生 proof-bound pass/fail。

## Immediate Documentation and Implementation Handoff

1. 把 `TASK_DEFINITION.md` 改成一个统一输出接口和四层证据；E1 历史适配与 E2 因果破坏继续分开计分和解释。
2. 在 `README.md` 和 `PLAN.md` 中明确候选仓由数据集提供，停止把开放世界关系发现作为主任务。
3. 保留既有主动项目包材料，但改称执行证据储备；停止要求新候选补齐 A3 或多仓负空间后才能计入 E2。
4. 先不改数据 schema；现有输入和预测格式足以运行主排序，证据不足统一使用 `not_assessed`。只有实际运行需要提交证据引用时，再提出 schema v2。
5. 审计当前候选目录 provenance，落地关系隔离 split，并重新盘点现有案例的 E1-E4 数量和构造成本，然后决定是否继续采集。
