# Marshal 跨仓评测缺口分析

**日期**：2026-08-22  
**范围**：基于现有代码审计、现成数据核验和当前 Marshal 原样试跑；不包含产品代码修改。

## 一、结论

Marshal 当前已经能命中预先登记的跨仓契约，也能把检查路由到另一个仓库；它不能把多个仓库的指定版本作为一次联合审查输入，也不能证明消费仓实际使用了上游候选版本。

原样试跑进一步表明，这不只是理论上的接口缺口：BeyondSWE、DepBench 和 BUMP 的 16 个目标仓或消费仓样本全部被归为通用中风险，跨仓契约命中数和可执行不变量数均为 0。对于 BUMP 中共享同一上游的多个消费仓，Marshal 只能看到彼此独立的 `pom.xml` 改动，无法利用数据中已经存在的共同依赖关系。

因此近期重点应是评测适配和任务表达，而不是先改审查推理逻辑。现有数据足以测量“仓外信息使用”和“依赖升级后单消费仓修复”，但不足以单独证明“多个未发布候选版本能否联合通过”。

## 二、已观察到的具体失败

| 失败场景 | 实际证据 | 归因 | Git、版本和普通测试为什么还不够 |
|---|---|---|---|
| 未登记项目的依赖升级没有检查计划 | 5 个 DepBench 样本均为中风险，契约和不变量为空；其中 3 个已重放出升级后失败、修复后通过 | 配置和数据映射缺失 | Git 和依赖版本足以描述样本，但现有入口没有把依赖关系映射为 Marshal 契约或执行计划 |
| 同一上游影响多个消费仓时被拆成独立任务 | BUMP 选择的 3 个上游组、6 个消费仓均独立分类，共同上游信息没有进入输入 | 任务表达缺失 | 各仓提交号和测试已经足以作为事实来源；缺的是一次任务中引用这些事实的结构，而不是新的哈希或冻结机制 |
| 异仓检查被正确标成未运行 | 自动报告器遇到 `location_repo != repo` 时记录 `not_run` 并降级 | 执行能力缺失 | 单仓测试不能代替在目标仓执行；但现阶段只需明确仓库路径和版本，不需要新增发布门禁 |
| 手工异仓检查可能使用错误组合 | 手工流程使用异仓当前主分支顶端，而不是显式候选版本 | 组合未验证 | 两个仓库各自的 Git 版本足以固定组合；普通单仓测试无法证明消费仓使用的是指定上游候选产物 |
| 仓库身份可能冲突 | GitHub 事件进入核心后只保留裸仓库名 | 输入信息丢失 | Git 本身能区分远程地址；需要保留 `owner/repo`，不需要额外主键系统 |
| 现成数据没有未发布多仓候选组合 | BeyondSWE 和 DepBench 每例只有一个目标仓；BUMP 使用已发布依赖版本 | 评测不匹配 | 这些数据能测部分能力，但无法构成两个待合并仓库版本的联合消费实验 |

## 三、失败类型统计

当前原样试跑的 16 个仓库输入中：

- 16 个得到通用中风险分类；
- 16 个契约命中为空；
- 16 个不变量计划为空；
- 0 个由自动执行器运行了跨仓检查；
- 0 个输入能够声明第二个仓库的候选版本；
- 0 个结果能够证明候选依赖被消费。

这里不把“审查维度中出现 `cross-repo`”记为跨仓发现。它只是通用审查提示，没有给出相关仓库、依赖方向、检查位置或执行证据。

## 四、最小设计方向

下一步设计只需要解决已经出现的失败，不引入永久依赖图、内容哈希、冻结契约或新的合并门禁。

### 1. 项目级任务描述

评测适配层需要能够提供：

- 项目标识；
- 每个仓库的完整 `owner/repo`、本地路径和 Git 版本；
- 有方向的提供方到消费方关系；
- 每个关系对应的依赖坐标或产物；
- 要运行的现有构建或测试命令；
- 如何让消费仓使用指定上游候选产物。

这些字段应先存在于评测清单中。没有原样评测证据支持前，不把它们升级为新的核心契约。

### 2. 分离三个结果

报告至少要区分：

1. 找到了可能受影响的仓库；
2. 在该仓库运行了检查；
3. 检查实际消费了指定候选版本。

当前 `not_run` 行为应保留。真正缺少的是“运行了，但版本组合不明”和“已确认消费候选版本”之间的区别。

### 3. 先做评测转换，不先改领域包

BeyondSWE、DepBench 和 BUMP 可先转换为统一的外部评测清单，再调用 Marshal 现有分类和计划接口。转换层负责保留数据集原始 Git 版本、依赖关系和测试命令，不把第三方项目规则写进 CowboyPack。

### 4. 联合执行只复用项目已有命令

候选组合验证优先采用项目已有机制，例如本地安装、工作区替换、Maven 本地仓库、包管理器路径覆盖或现有集成测试。只有某个具体项目证明这些方式无法确认消费版本时，才讨论额外证明机制。

## 五、数据策略判断

三个现成数据集应继续保留，但职责不同：

| 数据来源 | 保留用途 | 不应声称 |
|---|---|---|
| BeyondSWE | 仓外知识检索和单仓修复 | 多仓候选版本联合执行 |
| DepBench | 五类生态的依赖升级识别、修复和测试 | 上游源码候选与消费仓联合构建 |
| BUMP | 共享上游的多消费仓影响、升级前后动态证据 | 未发布上游候选版本验证 |

需要补充的小案例集应围绕 BUMP 的多消费仓分组组织，并明确它仍使用发布版本。之后再增加少量真实协调变更，专门测未发布候选组合；这两个层次不能混为同一个指标。

## 六、下一阶段判定

本轮证据对应计划中的第二种和第三种情况：

> Marshal 能表达固定跨仓检查位置，但不能结构化验证多仓候选组合；现成数据能覆盖分项能力，却不能完整覆盖项目级联合审查。

所以合理顺序是：先用 6 个 BUMP 消费仓形成最小多仓影响案例集，再补 2 至 4 个真实协调变更案例。产品实现应等到这些案例能够稳定重放、且失败模式重复出现之后再决定。
