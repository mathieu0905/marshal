# Marshal 跨仓评测下一步计划

**日期**：2026-08-22  
**范围**：只做调研、数据核验和评测设计；本阶段不修改 Marshal 产品代码。

## 一、结论

下一步不应立即自建完整数据集，也不应先扩写 Marshal 架构。

先回答两个更基础的问题：

1. Marshal 现有的多仓配置究竟已经覆盖了哪些能力；
2. 现成评测集能否测出这些能力的实际效果和边界。

执行顺序是：

```text
核对现有能力
  -> 核验现成评测集
  -> 用当前 Marshal 原样试跑
  -> 根据失败证据定位缺口
  -> 只补现成数据无法覆盖的少量多仓联合案例
```

本轮优先复用 BeyondSWE、公开版 DepBench 和 BUMP。只有在它们无法回答“多个相关仓库能否被联合审查”时，才补建小规模 Marshal 专用案例。

## 二、需要回答的问题

### 1. Marshal 当前能力

- 是否能在一次任务中声明多个仓库及各自版本；
- 是否能表达仓库之间的依赖方向；
- 是否会把相关仓库作为审查上下文，而不只是列出路径；
- 是否会在相关仓库中执行已有检查；
- 是否能判断实际执行时消费的是候选版本还是当前已发布版本；
- 无法执行跨仓验证时，报告是否明确区分“未验证”和“验证通过”。

这里首先做配置和执行路径审计，不预设 Marshal 缺少这些能力。结论按“现有即可使用、需要配置、现有不能表达”三类记录。

### 2. 现成评测集能测什么

| 评测集 | 现成规模 | 本轮用途 | 不能直接证明的能力 |
|---|---:|---|---|
| [BeyondSWE](https://github.com/AweAI-Team/BeyondSWE) | 500 个任务，其中 200 个跨仓任务 | 测量是否能发现并正确使用仓外信息 | 多个仓库候选版本的联合执行 |
| [DepBench](https://huggingface.co/datasets/Depbench/build_from_source) | 201 个任务，157 个仓库，5 类依赖生态 | 测量依赖升级后的影响定位和问题识别 | 完整上游仓快照、多消费仓联合审查 |
| [BUMP](https://github.com/chains-project/bump) | 571 个可重放 Maven 依赖破坏案例 | 测量升级前成功、升级后失败的动态识别能力 | 非 Maven 场景和官方多仓任务组织 |
| [Patch Backporting Benchmark](https://zenodo.org/records/21785770) | 1234 个补丁移植案例 | 作为跨版本、跨仓补丁影响的补充样本 | 项目依赖传播和协调变更 |

`DepRepair` 论文中的 95 例 DepBench 与 Hugging Face 上的 201 例同名数据暂不视为同一版本。正式采用前需要继续核对来源、许可证和构造方法。

## 三、工作阶段

### 阶段 A：审计 Marshal 现有跨仓能力

目标是确认“已经能做，只是需要配置”这件事到底成立到什么程度。

具体工作：

1. 找出多仓相关的配置入口、任务输入和示例；
2. 跟踪一次多仓配置从输入、仓库准备、审查到报告的完整路径；
3. 核对仓库身份、版本选择、依赖方向和执行位置；
4. 区分“读取另一个仓库代码”和“验证两个候选版本的组合”；
5. 整理现有能力矩阵。

产出文件：`MARSHAL_CROSS_REPO_CAPABILITY_AUDIT.md`。

能力矩阵至少包含：

| 能力 | 现有即可使用 | 需要配置 | 现有不能表达 | 证据位置 |
|---|---:|---:|---:|---|
| 多仓上下文 |  |  |  |  |
| 仓库间依赖方向 |  |  |  |  |
| 每仓独立版本 |  |  |  |  |
| 受影响仓库定位 |  |  |  |  |
| 相关仓库执行 |  |  |  |  |
| 候选版本消费确认 |  |  |  |  |
| 未验证状态表达 |  |  |  |  |

### 阶段 B：核验现成评测集

这一阶段不是重新构造数据，而是确认数据能否稳定下载、理解和重放。

#### BeyondSWE

- 从 200 个跨仓任务中抽取 10 个；
- 覆盖不同仓库、语言和外部信息类型；
- 检查每例是否给出了目标仓库、基准版本、测试和容器；
- 标注完成任务真正需要的仓外来源；
- 确认任务是否只包含一个目标仓库。

#### 公开版 DepBench

- 抽取 5 个任务，尽量覆盖 Maven、npm、Cargo、Go 和 Python；
- 核对基础版本、依赖升级补丁、开发者修复和测试命令；
- 至少重放 3 个不同生态的任务；
- 核对数据来源、许可证和任务是否真的由依赖升级触发；
- 检查隐藏测试是否泄漏到可见输入。

#### BUMP

- 沿用已识别的重复依赖升级分组；
- 先选择 3 个依赖提供方，每组至少 2 个消费仓；
- 重放升级前成功和升级后失败；
- 记录失败发生在编译、测试还是依赖解析阶段；
- 暂不先寻找额外的成功样本，避免数据准备挤掉实际重放。

产出文件：`READY_DATASET_AUDIT.md`，内容包括可下载性、可重放性、许可、样本结构、标签可信度和对 Marshal 的适用范围。

### 阶段 C：当前 Marshal 原样试跑

这一阶段只使用现有 Marshal 和现有配置能力，不修改产品代码。

建议试跑集合：

- BeyondSWE 跨仓任务 5 个；
- 公开版 DepBench 任务 5 个；
- BUMP 多消费仓分组 3 个。

每次运行记录：

- Marshal 实际看到哪些仓库和信息；
- 找到了哪些受影响仓库、文件和接口；
- 提出了什么问题；
- 是否执行了检查，执行发生在哪个仓库；
- 是否使用了候选依赖版本；
- 最终判断是否被测试结果支持；
- 没有完成的部分是配置问题、数据问题还是现有能力缺失。

本阶段先做能力测量，不新增比较系统，也不预设需要新机制。

产出文件：`AS_IS_EVALUATION.md`。

### 阶段 D：失败归因和设计判断

把试跑失败归入以下类别：

| 类别 | 含义 | 后续动作 |
|---|---|---|
| 配置缺失 | 现有能力存在，但没有正确提供仓库、版本或关系 | 补配置说明和示例 |
| 数据映射失败 | 评测集字段无法直接映射到 Marshal 输入 | 设计轻量转换方式 |
| 上下文不足 | 没有找到需要的仓外代码或文档 | 研究仓库选择和检索方式 |
| 组合未验证 | 能读多个仓库，但执行时没有消费候选版本 | 设计候选版本组合与消费证据 |
| 推理错误 | 所需信息和执行结果都存在，但判断仍错误 | 做错误分析，再决定是否需要调整审查流程 |
| 评测不匹配 | 数据本身无法测试多仓联合审查 | 进入阶段 E，补少量案例 |

只有出现可重复的具体失败后，才提出对应设计。普通配置、Git 版本、现有测试和构建已经足以解决的问题，不增加新机制。

产出文件：`CROSS_REPO_GAP_ANALYSIS.md`。

### 阶段 E：补充最小多仓联合案例集

仅当阶段 B 和 C 证明现成数据无法覆盖项目级联合审查时执行。

目标规模为 5 至 10 个案例，而不是重新建设大型评测集。候选来源优先级：

1. OpenDev/Zuul 中有明确跨仓依赖关系和历史执行结果的协调变更；
2. 同一组织下，上游变化实际触发多个消费仓修改的公开案例；
3. Cowboy 中能重放的真实仓库间产物消费案例。

每个案例只要求包含：

- 两个或以上相关仓库及对应 Git 版本；
- 可解释的依赖方向；
- 上游候选变化；
- 受影响或不受影响的消费仓；
- 可执行的构建、测试或模拟结果；
- 原始开发者修复或历史协调变更作为参考。

不默认增加内容哈希、冻结契约、永久依赖图或项目门禁。Git 版本、依赖清单、现有测试和可重放执行足以表达的内容，直接复用。

产出文件：`MARSHAL_MULTI_REPO_CASESET.md`。

## 四、记录指标

首轮只记录能直接回答研究问题的指标：

- 受影响仓库命中数、遗漏数和误报数；
- 问题是否被正确识别；
- 报告证据能否指向具体仓库、文件和接口；
- 实际执行覆盖了哪些仓库；
- 执行是否使用候选版本；
- 有证据支持的结论比例；
- 无法判断时是否明确报告未验证；
- 每例耗时和主要资源消耗。

样本量较小时以逐例结果和错误类型为主，不先追求复杂统计结论。

| 1 | Marshal 现有能力审计 | 0.5 至 1 天 | 能力矩阵 |

前四步完成前，不进入产品实现。

## 六、阶段性判断

根据前四步结果，后续有三种合理方向：

1. **现有能力基本足够**：只补配置、示例和评测适配，不设计新的跨仓核心机制；
2. **能看多仓但不能验证组合**：研究重点收敛到候选版本组合、相关仓执行和消费证据；
3. **现成数据无法测目标问题**：保留现成数据做分项评测，再补最小多仓联合案例集。

最终设计必须由原样试跑中的具体失败支撑，而不是先假定 Marshal 需要重构。
